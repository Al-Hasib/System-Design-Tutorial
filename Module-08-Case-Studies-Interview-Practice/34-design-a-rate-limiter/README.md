## Script

### Hook / Intro

You've studied the algorithms. You know token bucket from leaky bucket, and you can draw a sliding window counter on a whiteboard. But an interviewer doesn't just want the algorithm — they want to watch you build a rate limiter that survives contact with a real production system: hundreds of API gateway instances, tens of millions of users, and the very real possibility that your Redis cluster falls over at 2 a.m. That's what this video does. We're running a full mock interview, start to finish, for the classic prompt: "design a rate limiter for our API." We'll clarify requirements, size the system with real numbers, sketch the architecture, deep-dive the two or three components that actually separate a senior answer from a junior one, and then talk honestly about where this design breaks. This is a capstone video — it assumes you already know the algorithms from Module 6, so we're not re-deriving token bucket from scratch; we're using it as a building block.

### Step 1: Clarify Requirements

Every good interview answer starts here, not with a diagram. Functionally, we need to support several kinds of limits at once: per-user limits for authenticated traffic, per-IP limits to throttle anonymous or unauthenticated callers, and per-API-key limits for third-party integrations that might have different contract tiers — a free tier capped at 100 requests per minute, a paid tier at 10,000. We also want per-endpoint granularity, since `/login` and `/password-reset` need much tighter limits than `/search`, precisely because they're attractive targets for credential-stuffing attacks. When a client is over the limit, the contract is a standard HTTP `429 Too Many Requests` response with a `Retry-After` header telling the client when to come back. Rules need to be configurable without a redeploy — product and security teams change limits often.

Non-functionally, three constraints dominate the design. First, scale: this has to work correctly across the entire API gateway fleet, not one box. Second, latency overhead: the rate-limiter check sits on the hot path of literally every request the system receives, so it needs to add microseconds, not milliseconds. Third, and this is the one candidates most often skip — availability. The rate limiter is a piece of shared infrastructure that touches 100% of traffic; if it becomes a single point of failure, a rate limiter outage becomes a full API outage, which is a worse outcome than the abuse it was built to prevent. We'll explicitly design for that failure mode later.

### Step 2: Capacity Estimation

Let's put numbers on it. Say the API fleet handles 10 million requests per second globally at peak, spread across roughly 500 API gateway instances — about 20,000 requests per second per instance. Every one of those requests needs a rate-limit check. If we naively checked every single request against one centralized Redis cluster, that's 10 million Redis operations per second — and a well-tuned single Redis node tops out around 100,000-200,000 ops/sec, so an exact, synchronous check-every-request design would need on the order of 50-100 shards just to keep up, before we even talk about replication for durability. That number alone tells us something important: full precision on every request, against one logical store, doesn't scale — we'll need to relax that later.

Now memory. Say we're tracking 50 million unique rate-limit keys — active users plus API keys plus IP buckets. Using a sliding-window-counter scheme, each key needs roughly two integers (current window count, previous window count) plus a timestamp, maybe 24 bytes of actual data, but Redis's per-key overhead for a hash or string entry runs another 60-90 bytes. Call it about 120 bytes per key all-in. Fifty million keys times 120 bytes is roughly 6 GB of working set — comfortably shardable across a handful of Redis nodes, and small enough to keep almost entirely in memory with room for replicas. So memory isn't the hard constraint here; sustained write throughput to a shared store is.

### Step 3: High-Level Design

Client requests hit a load balancer, then land on an API gateway instance — the same layer covered in the load-balancing and API-gateway videos earlier in this course. The gateway hosts a rate-limiter component, either as embedded middleware or a fast sidecar call, which checks the request's identity (user ID, IP, or API key) against the configured limit for that identity and endpoint. That check is backed by a centralized, sharded Redis cluster holding the actual counters, so that no matter which of the 500 gateway instances a given client's requests land on, they're all reading and writing the same shared state. If the request is under the limit, it's forwarded to the appropriate downstream microservice; if it's over, the gateway short-circuits and returns `429` immediately, without ever bothering a downstream service. That single detail — reject at the edge, not deep in the call graph — is why rate limiting belongs at the gateway in the first place.

### Step 4: Deep Dive

**Algorithm choice per layer, from Module 6.** We don't use one algorithm everywhere. At the gateway, token bucket is the default: it tolerates the bursty-but-legitimate traffic pattern of a client that's idle for a while then fires off a batch of calls, while still enforcing a steady long-run rate — the same behavior we saw in Stripe's and AWS API Gateway's public rate-limit designs. For endpoints where we need a strictly smoothed outflow into a fragile downstream system, we reach for leaky bucket instead, queuing and draining at a constant rate. And where memory cost matters more than perfect precision, sliding window counter approximates a true sliding log cheaply — exactly the trade-off we walked through in the rate-limiting-algorithms video.

**Distributed counters, atomically, in Redis.** This is the part that actually separates senior answers from junior ones. A naive "read the counter, check it, increment it" is three separate operations, and under concurrency that's a race condition — two requests can both read a count of 99 against a limit of 100 and both get admitted, silently letting the client through at double the intended rate. The fix is to push the entire check-and-increment into a single atomic Lua script executed via Redis's `EVAL`, so the read, the token-refill math, and the decrement happen as one indivisible operation on Redis's single-threaded execution engine. This is also where the CAP/PACELC trade-off from Module 3 shows up concretely: a rate limiter doesn't need strict linearizable consistency across every replica — it needs low latency and availability far more than it needs perfect global precision, which is exactly why teams lean toward Redis's default availability-favoring, eventually-consistent replication rather than paying a consensus round trip on every request.

**Idempotency and retries, from Module 6.** Clients retry. If a request times out on the client side but actually succeeded on the server, and the client retries it, should that retry consume a second token? If the retried operation is itself idempotent (identified by an idempotency key), the rate limiter should recognize the duplicate and avoid double-charging the client's quota for what is logically one request — otherwise your retry-safety story and your rate-limiting story actively fight each other, and flaky networks end up punishing well-behaved clients.

**Enforcing limits at multiple layers.** A production system doesn't rate-limit in only one place. A client SDK can carry a local, optimistic token bucket to prevent obviously-doomed requests from ever leaving the client, giving instant feedback with zero network cost. The API gateway enforces the authoritative, global limit against Redis. And inside the service mesh, sidecars can enforce service-to-service limits so that one overloaded internal caller can't take down a shared internal dependency — the same edge-vs-internal split you saw with API gateways protecting external traffic.

### Step 5: Bottlenecks & Trade-offs

The centralized Redis store is both the solution and the new bottleneck. A single viral user or a single misbehaving API key concentrates enormous load onto one hash slot — the classic hot-key problem — and no amount of horizontal sharding of the overall keyspace fixes a hot key that all lands on one shard. Mitigations include local pre-aggregation at each gateway instance (count locally, sync to Redis every 50-100ms instead of every request) and accepting a small, bounded amount of over-admission in exchange for taking Redis out of the hot path on every single call — trading the exactness of sliding window log for the throughput of an approximate counter, which is precisely the accuracy-vs-performance axis from Module 6. Distributed clock skew across 500 gateway instances is a related danger for any timestamp-based window calculation; token bucket implementations that compute elapsed time inside the Redis Lua script, using Redis's own server clock as the single source of truth, sidestep skew between client machines entirely. And the question every interviewer eventually asks: what happens when the rate limiter itself — Redis, or the service in front of it — goes down? This is a direct callback to the circuit breaker pattern: wrap calls to the rate-limiting store in a circuit breaker, and when it trips, you must explicitly choose fail-open (let requests through, risking the very overload you built this to prevent) or fail-closed (reject everything, guaranteeing an outage). The right default for most public read traffic is fail-open with a conservative local fallback limit; for security-sensitive endpoints like login, fail-closed is usually the safer default, since an attacker actively wants the limiter down.

## Key Takeaways

- Clarify functional scope (per-user/IP/API-key, per-endpoint, configurable tiers) and non-functional constraints (scale, latency overhead, availability) before drawing anything.
- Ground capacity estimates in real numbers — request rate, Redis ops/sec ceiling, and memory per key — to justify why naive designs don't scale.
- Use token bucket, leaky bucket, or sliding window per layer based on whether you need burst tolerance, strict smoothing, or memory-cheap approximation.
- Atomic Lua scripts in Redis are the standard way to eliminate check-then-increment race conditions across many stateless gateway instances.
- Idempotency keys prevent retried requests from double-consuming a client's quota.
- Always design the failure mode: circuit-break calls to the rate limiter store and make an explicit fail-open vs fail-closed decision per endpoint sensitivity.
