# Probabilistic Data Structures: Bloom Filters, HyperLogLog & Count-Min Sketch

**কঠিনতার মাত্রা:** Advanced

## শেখার লক্ষ্যসমূহ

- probabilistic data structure-এর মূল ধারণাটি ব্যাখ্যা করা: একটি ছোট, সীমাবদ্ধ error rate-এর বিনিময়ে বিশাল মেমরি সাশ্রয় করা।
- একটি Bloom filter কীভাবে "আমি কি এটা আগে দেখেছি?" প্রশ্নের উত্তর দেয় এবং কেন এটি false positive দিতে পারে কিন্তু কখনও false negative দেয় না, তা বর্ণনা করা।
- HyperLogLog কীভাবে সামান্য, নির্দিষ্ট পরিমাণ মেমরি ব্যবহার করে একটি বিশাল stream-এ ইউনিক আইটেমের সংখ্যা অনুমান করে, তা ব্যাখ্যা করা।
- একটি Count-Min Sketch কীভাবে সীমাবদ্ধ, একমুখী error সহ একটি stream-এ আইটেমগুলোর frequency অনুমান করে, তা ব্যাখ্যা করা।
- সেই system design পরিস্থিতিগুলো চিনতে পারা যেখানে একটি আনুমানিক উত্তর কেবল গ্রহণযোগ্যই নয়, বরং একমাত্র বাস্তবসম্মত বিকল্প।

## স্ক্রিপ্ট

### শুরু / ভূমিকা

system design-এ কিছু প্রশ্নের একটি স্পষ্ট, নির্ভুল উত্তর থাকে যা স্কেলে হিসাব করা কেবল খুব ব্যয়বহুল। "এই মাসে আমরা যে বিলিয়ন request দেখেছি, তার মধ্যে এই নির্দিষ্ট request ID-টি কি আমরা আগেই প্রসেস করেছি?" "কয়েকশো মিলিয়ন পেজ ভিউয়ের মধ্যে আজ আমাদের সাইটে কতজন ইউনিক ভিজিটর এসেছিল?" "প্রতি সেকেন্ডে মিলিয়ন মিলিয়ন request-এর মধ্যে এই নির্দিষ্ট URL-টি মোটামুটি কত ঘন ঘন request করা হচ্ছে?" প্রতিটি ID, প্রতিটি ইউনিক ভিজিটর, প্রতিটি URL-এর নির্ভুল সংখ্যা সংরক্ষণ করা — এটা একটা প্রকৃত, এবং কখনও কখনও নিষিদ্ধরকম, মেমরি খরচের বিষয়। আজ আমরা তিনটি probabilistic data structure নিয়ে আলোচনা করব যা "নির্ভুল কিন্তু ব্যয়বহুল" গ্রহণযোগ্য না হয়ে উঠলেই বারবার সামনে আসে: Bloom filter, HyperLogLog, এবং Count-Min Sketch। প্রতিটিই ইচ্ছাকৃতভাবে একটি ছোট, সুনির্দিষ্টভাবে সীমাবদ্ধ error-এর বিনিময়ে মেমরিতে নাটকীয় হ্রাস আনে।

### Bloom Filters: "আমি কি এটা আগে দেখেছি?"

একটি Bloom filter set-membership প্রশ্নের উত্তর দেয় — "এই এলিমেন্টটি কি সম্ভবত সেটের মধ্যে আছে?" — আসল এলিমেন্টগুলো সংরক্ষণ না করে একটি নির্দিষ্ট আকারের bit array এবং কয়েকটি independent hash function ব্যবহার করে। একটি এলিমেন্ট যোগ করতে, আপনি প্রতিটি hash function দিয়ে এটি চালান, এবং array-তে ফলস্বরূপ প্রতিটি position-এর bit-কে 1 সেট করেন। একটি এলিমেন্ট সেটে থাকতে পারে কি না তা যাচাই করতে, আপনি একইভাবে এটি hash করেন এবং দেখেন সেই সব bit position *সবগুলো* 1 কিনা। যদি এর একটিও 0 হয়, তাহলে এলিমেন্টটি নিশ্চিতভাবে সেটে নেই। যদি সবগুলো 1 হয়, তাহলে এলিমেন্টটি *সম্ভবত* সেটে আছে — কিন্তু এটি একটি **false positive** হতে পারে, যেখানে সম্পর্কহীন এলিমেন্টগুলো একসাথে ঠিক একই bit-গুলো চালু করে ফেলেছে। গুরুত্বপূর্ণভাবে, একটি Bloom filter কখনও **false negative** তৈরি করতে পারে না — যদি এটি বলে "উপস্থিত নেই," তা সবসময় সঠিক, কারণ একটি এলিমেন্ট যোগ করা শুধু bit সেট করে, কখনও unset করে না।

এই অসামঞ্জস্যতাই ঠিক কারণ যে কেন Bloom filter একটি ব্যয়বহুল, authoritative check-এর সামনে একটি সস্তা, দ্রুত pre-check হিসেবে এত উপযোগী: LSM-tree ভিডিওটি থেকে মনে করুন, একটি database read একটি সম্পূর্ণ SSTable এড়িয়ে যেতে পারে যদি এর Bloom filter বলে যে key নিশ্চিতভাবে সেখানে নেই — সাধারণ ক্ষেত্রে একটি disk read সাশ্রয় করে, এবং শুধুমাত্র বিরল false positive-এর ক্ষেত্রে একটি ধীর, নির্ভুল check-এর জন্য মূল্য পরিশোধ করে। অন্যান্য ক্লাসিক ব্যবহার: একটি web crawler "আমি কি ইতিমধ্যে এই URL-টি crawl করেছি?" যাচাই করছে, প্রতিটি দেখা URL সংরক্ষণ না করে, বা একটি spam filter "আমি কি এই ম্যালিশাস কনটেন্টের এই নির্দিষ্ট hash আগে দেখেছি?" যাচাই করছে। bit array-এর আকার এবং hash function-এর সংখ্যা false-positive rate টিউন করে — বড় array এবং বেশি hash function মানে কম false positive, কিন্তু তার বিনিময়ে বেশি মেমরি খরচ হয়।

### HyperLogLog: "প্রায় কতগুলো ইউনিক আইটেম?"

একটি বিশাল stream-এ নির্ভুল ইউনিক আইটেম (cardinality) গণনা করার জন্য স্বাভাবিকভাবেই প্রতিটি দেখা ইউনিক আইটেম সংরক্ষণ করা লাগে — মূলত একটি hash set — যা বিলিয়ন বিলিয়ন আইটেমের জন্য বিশাল মেমরি দাবি করতে পারে। **HyperLogLog** hash function output সম্পর্কে একটি চতুর পর্যবেক্ষণ ব্যবহার করে এই সংখ্যা অনুমান করে: একটি র‍্যান্ডম-দেখতে hash-এর জন্য, ধরুন 10টি leading zero bit সহ একটি hash value দেখার সম্ভাবনা হলো 1,024-এর মধ্যে 1টি — সুতরাং যদি আপনি এত সংখ্যক leading zero সহ একটি hash পর্যবেক্ষণ করে থাকেন, এটি পরিসংখ্যানগত প্রমাণ যে আপনি সম্ভবত মোটামুটি সেই সংখ্যক *distinct* আইটেম hash করেছেন (কারণ বেশি distinct আইটেম মানে অস্বাভাবিকভাবে দীর্ঘ leading zero-এর run সহ একটি hash দেখার বেশি সুযোগ)। HyperLogLog অনেকগুলো independent bucket জুড়ে পর্যবেক্ষণ করা সর্বোচ্চ leading zero সংখ্যা ট্র্যাক করে (প্রতিটি আগত আইটেমকে, ধরুন, 16,384টি bucket-এর একটিতে hash করে, এবং প্রতি bucket-এ সর্বোচ্চ leading-zero count ট্র্যাক করে), এরপর একটি নির্দিষ্ট averaging formula ব্যবহার করে সব bucket-এর অনুমান একত্রিত করে একটি চূড়ান্ত cardinality অনুমান পেতে। ফলাফলটি সত্যিই লক্ষণীয়: HyperLogLog বিলিয়ন বিলিয়ন ইউনিক এলিমেন্ট সহ একটি সেটের cardinality প্রায় 1-2% error-এর মধ্যে অনুমান করতে পারে, মাত্র কয়েক কিলোবাইট মেমরি ব্যবহার করে — প্রকৃত cardinality হাজার হোক বা বিলিয়ন হোক তা নির্বিশেষে। এটাই ঠিক Redis-এর `PFCOUNT` এবং বেশিরভাগ বড়-স্কেল ওয়েব analytics platform-এ "ইউনিক ভিজিটর" কাউন্টারের পেছনের শক্তি।

### Count-Min Sketch: "প্রায় কত ঘন ঘন?"

যেখানে Bloom filter উত্তর দেয় "এটা কি সেটে আছে" এবং HyperLogLog উত্তর দেয় "কতগুলো ইউনিক আইটেম," সেখানে একটি **Count-Min Sketch** উত্তর দেয় "এই নির্দিষ্ট আইটেমটি আনুমানিক কতবার ঘটেছে?" — একটি frequency-estimation সমস্যা, যা counter-এর একটি 2D array এবং একাধিক hash function ব্যবহার করে সমাধান করে। একটি আইটেমের ঘটনা রেকর্ড করতে, আপনি একে কয়েকটি hash function দিয়ে hash করেন (প্রতিটি 2D array-এর একটি ভিন্ন row-এ ম্যাপ হয়) এবং ফলস্বরূপ প্রতিটি position-এর counter বাড়ান। একটি আইটেমের frequency অনুমান করতে, আপনি একইভাবে এটি hash করেন এবং আপনি যেসব counter-এ পৌঁছান তাদের মধ্যে *সর্বনিম্ন* মানটি নেন — বিশেষভাবে সর্বনিম্ন মানটি নেওয়া হয় কারণ hash collision শুধুমাত্র একটি counter-কে ফুলিয়ে তুলতে পারে (একাধিক ভিন্ন আইটেম একই cell বাড়ায়), কখনও কমাতে পারে না, তাই কয়েকটি independent অনুমানের মধ্যে সবচেয়ে ছোটটি সঠিকের সবচেয়ে কাছাকাছি হয়। একটি Bloom filter-এর মতো, এর মানে হলো Count-Min Sketch-এর error কঠোরভাবে একমুখী: এটি একটি আইটেমের প্রকৃত frequency-কে (collision-এর কারণে) বেশি অনুমান করতে পারে কিন্তু কখনও কম অনুমান করবে না। এটিই বিশাল স্কেলে "trending topics" এবং "top-K most frequent items" ফিচারের পেছনের টুল — সিস্টেম যে সম্ভাব্য প্রতিটি search term, hashtag, বা URL দেখতে পারে, তার প্রতিটির জন্য একটি নির্ভুল counter সত্যিই সামর্থ্য করা যায় না, কিন্তু আপনি একটি নির্দিষ্ট আকারের sketch-এর সামর্থ্য রাখতে পারেন যা সত্যিই গুরুত্বপূর্ণগুলোর জন্য নির্ভরযোগ্যভাবে কাছাকাছি একটি অনুমান দেয়।

### সাধারণ সূত্র

তিনটি structure-ই একই মৌলিক ট্রেড-অফ শেয়ার করে: একটি নির্দিষ্ট, ছোট মেমরি ফুটপ্রিন্ট যা আপনি যে ডেটা সারসংক্ষেপ করছেন তার আকারের সাথে বাড়ে না, তার বিনিময়ে একটি নিয়ন্ত্রিত, গাণিতিকভাবে বোঝা যায় এমন error rate — কখনও অসীম বা অপ্রত্যাশিত নয়। এদের কোনোটিই উপযুক্ত নয় যখন আপনার একটি নির্ভুল উত্তর প্রয়োজন (একটি ব্যাংক ব্যালেন্স, একটি ইনভেন্টরি গণনা যা কখনও ভুল হতে পারে না) — এগুলো বিশেষভাবে সেই শ্রেণীর সমস্যার জন্য যেখানে "বিশাল মেমরি খরচে একদম সঠিক" এবং "সামান্য মেমরি খরচে খুব কাছাকাছি" একই বাস্তবসম্মত ব্যবসায়িক ফলাফল তৈরি করে, যা প্রকৃত system design সমস্যার একটি বিস্ময়করভাবে বড় শ্রেণী হয়ে দাঁড়ায়।

### বাস্তব-বিশ্বের উদাহরণ

একটি বড়-স্কেল ad click ট্র্যাকিং সিস্টেমের কথা বিবেচনা করুন। ক্লিকগুলো ডুপ্লিকেট বাদ দেওয়া (প্রতিদিন বিলিয়ন বিলিয়নের মধ্যে এই নির্দিষ্ট ক্লিক ID কি ইতিমধ্যে রেকর্ড করা হয়েছে?) একটি স্বাভাবিক Bloom filter প্রয়োগ — authoritative, নির্ভুল ডেটা স্টোর স্পর্শ করার আগে একটি সস্তা প্রথম check, যেখানে বিরল false positive-এর মূল্য শুধুমাত্র সামান্য অতি-সতর্ক এড়িয়ে যাওয়া, কোনো প্রকৃত সঠিকতার সমস্যা নয়। একটি নির্দিষ্ট ad ক্যাম্পেইনে ক্লিক করা ইউনিক ইউজারদের গণনা করতে HyperLogLog ব্যবহার করা হয় — বিজ্ঞাপনদাতারা "মোটামুটি কতজন ইউনিক মানুষ" নিয়ে চিন্তিত, ব্যক্তি-প্রতি-সঠিক একটি সংখ্যা নয়, এবং এটি বিলিয়ন বিলিয়ন ইভেন্টের উপর টেরাবাইটের পরিবর্তে কিলোবাইট মেমরি ব্যবহার করে চালানো যায়। এবং লক্ষ লক্ষ সক্রিয় ক্যাম্পেইনের মধ্যে near real-time-এ শীর্ষ 10টি সর্বোচ্চ-ক্লিক করা ad ক্যাম্পেইন চিহ্নিত করতে একটি Count-Min Sketch ব্যবহার করা হয় প্রতিটি ক্যাম্পেইন ID-এর আনুমানিক ক্লিক frequency ট্র্যাক করতে, যথেষ্ট সস্তায় যাতে প্রতিটি ক্লিকে আপডেট করা যায়, প্রকৃতপক্ষে উচ্চ-frequency ক্যাম্পেইনগুলোকে সামনে নিয়ে আসে, এমন প্রতিটি ক্যাম্পেইনের জন্য একটি নির্ভুল counter ছাড়াই যা কখনওই top 10-এ থাকবে না।

### সংক্ষিপ্তসার

Probabilistic data structure একটি ছোট, সুনির্দিষ্টভাবে সীমাবদ্ধ error rate-এর বিনিময়ে মেমরিতে নাটকীয় হ্রাস আনে, এবং এটিই সঠিক টুল ঠিক তখন যখন একটি আনুমানিক উত্তর ব্যবসায়িক সমস্যার জন্য সত্যিই যথেষ্ট ভালো। Bloom filter শূন্য false negative এবং একটি টিউনযোগ্য false-positive rate সহ set-membership প্রশ্নের উত্তর দেয় — একটি ব্যয়বহুল নির্ভুল লুকআপের সামনে একটি সস্তা pre-check। HyperLogLog মাত্র কয়েক কিলোবাইট মেমরি ব্যবহার করে এবং প্রায় 1-2% error সহ বিশাল stream-এ ইউনিক গণনা (cardinality) অনুমান করে। Count-Min Sketch একমুখী (শুধুমাত্র বেশি-অনুমান) error সহ আইটেম frequency অনুমান করে, স্কেলে top-K এবং trending-item ফিচারের শক্তি যোগায়। তিনটির কোনোটিরই নাগাল নেওয়া উচিত নয় যখন একটি উত্তর নির্ভুল হতে হবে — এগুলো বিশেষভাবে সেখানেই তাদের স্থান অর্জন করে যেখানে "যথেষ্ট কাছাকাছি" এবং "সম্পূর্ণ সঠিক" একই বাস্তব-বিশ্বের ফলাফল তৈরি করে।

### এরপর কী

এখানেই distributed coordination এবং scale techniques সম্পর্কিত এই module-টি শেষ হচ্ছে। পরবর্তী module একটি ভিন্ন, সমান গুরুত্বপূর্ণ বিষয়ে সরে যায়: একবার লাইভ হয়ে গেলে এরকম একটি সিস্টেম আপনি প্রকৃতপক্ষে কীভাবে observe, deploy এবং operate করেন — logging, metrics, tracing, container, deployment strategy, এবং একটি distributed system সত্যিই failure থেকে বেঁচে থাকে কিনা তা কীভাবে পরীক্ষা করা যায়।

## মূল বিষয়সমূহ (Key Takeaways)

- Probabilistic data structure নির্ভুল ডেটা সংরক্ষণের তুলনায় একটি ছোট, গাণিতিকভাবে সীমাবদ্ধ error rate-এর বিনিময়ে নাটকীয়ভাবে হ্রাসকৃত, নির্দিষ্ট মেমরি ব্যবহার করে।
- একটি Bloom filter শূন্য false negative সহ (যদি এটি না বলে, তা নিশ্চিত) এবং একটি টিউনযোগ্য false-positive rate সহ "আমি কি এটা দেখেছি?" প্রশ্নের উত্তর দেয় — একটি ব্যয়বহুল, authoritative লুকআপের আগে একটি সস্তা pre-check।
- HyperLogLog মাত্র কয়েক কিলোবাইট মেমরি ব্যবহার করে একটি বিশাল stream-এ ইউনিক আইটেমের সংখ্যা (cardinality) প্রায় 1-2% error-এর মধ্যে অনুমান করে, প্রকৃত cardinality যাই হোক না কেন।
- Count-Min Sketch একমুখী (শুধুমাত্র বেশি-অনুমান) error সহ আইটেম frequency অনুমান করে, প্রতি-আইটেম একটি নির্ভুল counter ছাড়াই top-K/trending-item ফিচারের শক্তি যোগায়।
- এদের কোনোটিই উপযুক্ত নয় যখন একটি উত্তর নির্ভুল হতে হবে (আর্থিক ব্যালেন্স, ইনভেন্টরি) — এগুলো সেই বৃহৎ শ্রেণীর সমস্যার জন্য যেখানে "যথেষ্ট কাছাকাছি" এবং "সম্পূর্ণ সঠিক" একই বাস্তবসম্মত ফলাফল তৈরি করে।
