# অনুশীলন ও ইন্টারভিউ প্রশ্ন

**১. সব probabilistic data structure কোন মূল trade-off করে?**
এগুলো নির্ভুল ডেটা সংরক্ষণের তুলনায় একটি ছোট, গাণিতিকভাবে সীমাবদ্ধ error rate-এর বিনিময়ে মেমরি ব্যবহারে একটি নাটকীয়, নির্দিষ্ট হ্রাস করে — এবং সেই মেমরি ফুটপ্রিন্ট সাধারণত অন্তর্নিহিত dataset-এর আকারের সাথে বাড়ে না, যেমনটা নির্ভুল storage-এর ক্ষেত্রে হতো।

**২. একটি Bloom filter কেন false positive দিতে পারে কিন্তু কখনো false negative দেয় না?**
একটি এলিমেন্ট যোগ করা শুধুমাত্র array-এর bit-গুলো 1-এ সেট করে, কখনো unset করে না। যদি একটি নির্দিষ্ট এলিমেন্টের জন্য যাচাই করা যেকোনো bit এখনো 0 থাকে, তাহলে সেই এলিমেন্টটি নিশ্চিতভাবে কখনো যোগ করা হয়নি — একটি নিশ্চিত উত্তর। কিন্তু যদি সব যাচাই করা bit 1 হয়, তাহলে হতে পারে অন্যান্য, সম্পর্কহীন এলিমেন্টগুলো একসাথে ঠিক একই bit সেট করে ফেলেছে (একটি false positive), যদিও এই নির্দিষ্ট এলিমেন্টটি কখনো যোগ করা হয়নি।

**৩. একটি ব্যয়বহুল, authoritative লুকআপের সামনে (যেমন, একটি LSM-tree SSTable check) একটি Bloom filter কেন pre-check হিসেবে উপযোগী?**
কারণ Bloom filter থেকে একটি "নিশ্চিতভাবে উপস্থিত নেই" উত্তর আপনাকে সম্পূর্ণ আত্মবিশ্বাসের সাথে ব্যয়বহুল লুকআপটি সম্পূর্ণভাবে এড়িয়ে যেতে দেয়, এবং একটি ভালোভাবে টিউন করা filter-এর জন্য এটাই সাধারণ ক্ষেত্র। বিরল false positive-এর মূল্য শুধুমাত্র একটি অপ্রয়োজনীয় কিন্তু ক্ষতিহীন ব্যয়বহুল লুকআপ — কখনো একটি ভুল চূড়ান্ত উত্তর নয়, কারণ filter যখনই "হয়তো" বলে তখন authoritative check তখনও সংঘটিত হয়।

**৪. HyperLogLog-এর cardinality অনুমানের পেছনের পরিসংখ্যানগত ধারণাটি ব্যাখ্যা করুন।**
র‍্যান্ডম-দেখতে hash value-এর জন্য, leading zero bit-এর একটি অস্বাভাবিক দীর্ঘ run পর্যবেক্ষণ করা বিরল — N সংখ্যক leading zero সহ একটি hash-এর সম্ভাবনা মোটামুটি 1-in-2^N। এই ধরনের দীর্ঘ run দেখাই তাই পরিসংখ্যানগত প্রমাণ যে অনেক distinct আইটেম hash করা হয়েছে, কারণ বেশি distinct আইটেম মানে একটি বিরল, দীর্ঘ run পর্যবেক্ষণ করার বেশি সুযোগ। HyperLogLog অনেক bucket জুড়ে প্রতি bucket-এ সর্বোচ্চ leading-zero run ট্র্যাক করে এবং সেগুলোকে একটি cardinality অনুমানে একত্রিত করে।

**৫. প্রকৃত cardinality যাই হোক না কেন, HyperLogLog মোটামুটি কী নির্ভুলতা এবং মেমরি ফুটপ্রিন্ট অর্জন করে?**
মোটামুটি 1-2% আপেক্ষিক error, মাত্র কয়েক কিলোবাইট মেমরি ব্যবহার করে — ইউনিক আইটেমের প্রকৃত সংখ্যা হাজারে হোক বা বিলিয়নে হোক, মেমরি ব্যবহার মূলত নির্দিষ্টই থাকে।

**৬. একটি Count-Min Sketch কীভাবে একটি আইটেমের frequency অনুমান করে, এবং কেন এটি hash করা position-গুলোর মধ্যে গড় না নিয়ে সর্বনিম্নটি নেয়?**
এটি আইটেমটিকে বেশ কয়েকটি independent hash function দিয়ে hash করে, প্রতিটি একটি 2D array-এর ভিন্ন row-এর একটি counter নির্দেশ করে, এবং প্রতিটি ঘটনায় প্রতিটি counter বাড়ায়। Frequency অনুমান করতে, এটি একই position দেখে এবং সর্বনিম্ন মান নেয়। এটি সর্বনিম্নটি ব্যবহার করে কারণ অন্যান্য আইটেমের সাথে hash collision শুধুমাত্র একটি counter ফুলিয়ে তুলতে পারে (কখনো কমাতে পারে না), তাই কয়েকটি independent, সম্ভবত-ফোলানো অনুমানের মধ্যে সবচেয়ে ছোটটি প্রকৃত মানের সবচেয়ে কাছাকাছি।

**৭. Count-Min Sketch-এর error কেন "একমুখী" হিসেবে বর্ণনা করা হয়?**
কারণ একই hash bucket শেয়ার করা ভিন্ন আইটেমগুলোর মধ্যে collision শুধুমাত্র একটি counter-কে খুব বেশি করতে পারে (অতি-অনুমান), কখনো খুব কম নয় — তাই একটি Count-Min Sketch অনুমান হয় একদম সঠিক অথবা একটি অতি-অনুমান, এবং কখনো একটি আইটেমের প্রকৃত frequency-কে কম অনুমান করে না।

**৮. পরিস্থিতি: প্রতি মাসে প্রসেস করা বিলিয়ন বিলিয়নের মধ্যে, একই payment transaction ID দুবার প্রসেস করা প্রতিরোধ করতে হবে, প্রতিটি ID চিরকাল সংরক্ষণ না করে। কোন structure উপযুক্ত, এবং শুধু এটি একা ব্যবহার করার ঝুঁকি কী?**
একটি Bloom filter "আমি কি এই ID আগে দেখেছি?" প্রশ্নের জন্য একটি দ্রুত, মেমরি-সাশ্রয়ী প্রথম check হিসেবে উপযুক্ত। শুধু এটির উপর নির্ভর করার ঝুঁকি হলো এর false-positive rate — এটি মাঝে মাঝে একটি আসলে নতুন transaction ID-এর জন্য "আগে দেখা হয়েছে" বলতে পারে, ভুলভাবে এটি এড়িয়ে যেতে পারে। payment deduplication-এর মতো গুরুত্বপূর্ণ কিছুর জন্য, filter যে কোনো ID-কে "হয়তো দেখা হয়েছে" বলে চিহ্নিত করে তার জন্য একটি authoritative check-এর (যেমন, একটি database লুকআপ) সাথে এটিকে জোড়া দেওয়া উচিত, filter "হ্যাঁ" বললে সরাসরি বিশ্বাস করার পরিবর্তে।

**৯. পরিস্থিতি: একটি সোশ্যাল মিডিয়া প্ল্যাটফর্ম প্রতি মিনিটে ব্যবহৃত লক্ষ লক্ষ hashtag-এর মধ্যে near real-time-এ "trending hashtag" প্রদর্শন করতে চায়। কোন structure উপযুক্ত, এবং কেন?**
Count-Min Sketch — প্ল্যাটফর্মের প্রতিটি hashtag-এর জন্য যথেষ্ট সস্তায় একটি আনুমানিক frequency গণনা দরকার যাতে প্রতিটি পোস্টে আপডেট করা যায়, এমন প্রতিটি hashtag-এর জন্য একটি নির্ভুল counter বজায় না রেখে যা কখনোই trending-এর কাছাকাছি হবে না। একমুখী অতি-অনুমান error একটি গ্রহণযোগ্য trade-off কারণ প্রকৃতপক্ষে উচ্চ-frequency hashtag গুলো noise-এর উপরে স্পষ্টভাবে আলাদা হয়ে থাকবে।

**১০. সত্য না মিথ্যা: Bloom filter, HyperLogLog, এবং Count-Min Sketch-এর মতো probabilistic data structure একটি ব্যাংক অ্যাকাউন্ট ব্যালেন্স ট্র্যাক করার জন্য উপযুক্ত।**
মিথ্যা। এই structure গুলো এমন পরিস্থিতির জন্য ডিজাইন করা হয়েছে যেখানে একটি আনুমানিক উত্তর একটি গ্রহণযোগ্য বাস্তবসম্মত ফলাফল দেয়। একটি ব্যাংক অ্যাকাউন্ট ব্যালেন্সের প্রতিবার একটি নির্ভুল, সঠিক মান প্রয়োজন — এখানে একটি probabilistic structure ব্যবহার করলে প্রকৃত আর্থিক পরিণতি সহ error তৈরি হতে পারে, যা ঠিক সেই শ্রেণীর সমস্যা যার জন্য এই টুলগুলো তৈরি নয়।
