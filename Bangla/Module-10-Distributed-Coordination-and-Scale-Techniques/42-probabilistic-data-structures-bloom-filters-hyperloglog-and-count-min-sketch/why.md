# কেন এই বিষয়টি গুরুত্বপূর্ণ: Probabilistic Data Structures

> **এক বাক্যে:** কিছু প্রশ্ন এত বেশি জিজ্ঞাসা করা হয়, এত বড় সেট সম্পর্কে, যে একটি নির্ভুল উত্তরের খরচ সেই উত্তরের মূল্যের চেয়েও বেশি হয়ে যায় — এবং 1% error rate মেনে নিলে খরচ হাজার গুণ কমিয়ে ফেলা যায়।

## এই ধারণার আগের পৃথিবী

তিনটি সাধারণ শোনানো প্রয়োজনীয়তা, প্রতিটিই নির্ভুল data structure ব্যবহার করে স্কেলে অসম্ভব হয়ে ওঠে:

**"এই ইউজার কি এই আর্টিকেলটি দেখেছে?"** 100 মিলিয়ন ইউজার এবং 10 মিলিয়ন আর্টিকেল থাকলে, দেখা-জোড়ার একটি সেট সম্ভাব্যভাবে বিশাল হতে পারে। এটিকে নির্ভুলভাবে সংরক্ষণ করার মানে হলো শত শত গিগাবাইট এবং প্রতিটি check-এর জন্য একটি network call।

**"আজ আমাদের কতজন ইউনিক ভিজিটর ছিল?"** নির্ভুল uniqueness-এর জন্য আপনি যে প্রতিটি ভিজিটর ID দেখেছেন তা মনে রাখা প্রয়োজন। হাজার হাজার dimension (প্রতি পেজ, প্রতি দেশ, প্রতি ঘণ্টা) জুড়ে এক বিলিয়ন ইভেন্টের জন্য, আপনি শুধু গণনা করার জন্য raw data আবার সংরক্ষণ করছেন।

**"এখন শীর্ষ 100টি trending hashtag কী কী?"** নির্ভুল গণনার মানে হলো প্রতিটি distinct hashtag-এর জন্য একটি counter। লক্ষ লক্ষ distinct value, যাদের বেশিরভাগ একবারই দেখা যায়, এবং আপনি একটি hash map বজায় রাখছেন যা কখনও বাড়া থামে না — একটি stream processor-এর মেমরিতে যা real time-এর সাথে তাল মিলিয়ে চলতে হয়।

এই সম্পদগুলো একটি নির্ভুল উত্তরের মূল্যের তুলনায় অত্যন্ত অসামঞ্জস্যপূর্ণ। ঠিক 4,821,338 জন ইউনিক ভিজিটর ছিল তা কারো জানার প্রয়োজন নেই; "প্রায় 4.82 মিলিয়ন" একই ব্যবসায়িক তথ্য।

## এটি যে সমস্যাগুলো সমাধান করে

### 1. সাধারণত অনুপস্থিত জিনিসের জন্য ব্যয়বহুল লুকআপ
**আপনি যা দেখেন:** cache এবং database লুকআপের একটি উচ্চ হার যা কিছুই ফেরত দেয় না — একটি key আছে কিনা, একটি URL crawl করা হয়েছে কিনা, একটি username নেওয়া হয়েছে কিনা তা যাচাই করা।

**কেন এটি ঘটে:** প্রতিটি check-এর খরচ একটি disk read বা network round trip, এমনকি যখন উত্তর "না" হয়, এবং "না"-ই সাধারণ ক্ষেত্র।

**Bloom filter কীভাবে এটি সমাধান করে:** একটি Bloom filter একটি bit array এবং কয়েকটি hash function ব্যবহার করে "নিশ্চিতভাবে সেটে নেই" অথবা "সম্ভবত সেটে আছে" এই উত্তর দেয় — লক্ষ লক্ষ আইটেমের জন্য কয়েক মেগাবাইট, কোনো false negative ছাড়াই। একটি "নিশ্চিতভাবে নেই" উত্তর ব্যয়বহুল লুকআপকে সম্পূর্ণভাবে এড়িয়ে যায়। এটাই ঠিক কারণ যে কেন প্রতিটি **LSM-tree storage engine** প্রতিটি on-disk ফাইলের সামনে একটি Bloom filter বসায়, এবং কেন এগুলো cache penetration-এর বিরুদ্ধে standard defense। অসামঞ্জস্যতাই পুরো কৌশল: false positive আপনার একটি অপ্রয়োজনীয় লুকআপের খরচ করায়, যা আপনি ইতিমধ্যেই পরিশোধ করছিলেন।

### 2. Cardinality গণনা যা মেমরিতে ধরে না
**আপনি যা দেখেন:** ইউনিক-ভিজিটর, ইউনিক-ডিভাইস, বা ইউনিক-সার্চ-টার্ম গণনা, যেখানে অনেক dimension জুড়ে প্রতিটি identifier সংরক্ষণ করা প্রয়োজন।

**কেন এটি ঘটে:** নির্ভুল distinct গণনার জন্য মূলত আপনি ইতিমধ্যে কী দেখেছেন তা মনে রাখা দরকার।

**HyperLogLog কীভাবে এটি সমাধান করে:** এটি hash করা value-গুলোর পরিসংখ্যানগত বণ্টন থেকে cardinality অনুমান করে, প্রায় **12 KB ব্যবহার করে বিলিয়ন বিলিয়ন distinct আইটেম গণনা করে** প্রায় 2% error সহ — একটি নির্দিষ্ট, ক্ষুদ্র পরিমাণ মেমরি, আইটেম সংখ্যা যাই হোক না কেন। গুরুত্বপূর্ণভাবে, HLL sketch গুলো **merge** করা যায়: আপনি প্রতি পেজের প্রতি ঘণ্টায় একটি রাখতে পারেন এবং পুনরায় গণনা না করেই দৈনিক বা সাইট-ব্যাপী uniques পেতে সেগুলো একত্রিত করতে পারেন। সেই mergeability-ই এটিকে analytics-এর জন্য ব্যবহারিক করে তোলে, এবং এটি একটি built-in Redis type হিসেবে পাওয়া যায়।

### 3. দীর্ঘ tail-এর জন্য frequency ট্র্যাকিং যা আপনি সংরক্ষণ করতে পারেন না
**আপনি যা দেখেন:** Trending topics, heavy-hitter detection, অথবা লক্ষ লক্ষ key জুড়ে per-key rate limiting, যেখানে প্রতি key-তে একটি counter অত্যধিক।

**কেন এটি ঘটে:** বেশিরভাগ key একবার বা দুবার দেখা যায়; আপনি noise-এ প্রধান একটি বণ্টনের জন্য সম্পূর্ণ storage খরচ করছেন।

**Count-Min Sketch কীভাবে এটি সমাধান করে:** counter-এর একটি নির্দিষ্ট আকারের 2D array, প্রতিটি আইটেম প্রতি row-তে একটি cell-এ hash করা হয়। Frequency অনুমান প্রকৃত value-কে ছাড়িয়ে যেতে পারে (collision যোগ করে), কখনও কম হয় না। যেহেতু আপনি heavy hitter খুঁজছেন, বিরল আইটেমের সামান্য অতি-অনুমান ক্ষতিহীন — ঘন ঘন আইটেমগুলো তখনও প্রাধান্য পায়। ধ্রুবক মেমরি, এবং এটি একটি stream-এ এক পাসে কাজ করে।

### 4. যেখানে নির্ভুলতা প্রয়োজন ছিল সেখানে অনুমান ব্যবহার করা
**আপনি যা দেখেন:** একজন ইউজারকে ইতিমধ্যে চার্জ করা হয়েছে কিনা তা যাচাই করতে একটি Bloom filter ব্যবহার করা হয়েছে, এবং একটি দুর্ভাগ্যজনক false positive-এর মানে একজন গ্রাহককে কখনও বিল করা হবে না।

**কেন এটি ঘটে:** ব্যবসায়িক পরিণতির বিরুদ্ধে error mode-টি পুরোপুরি চিন্তা করা হয়নি।

**guarantee গুলো বোঝা কীভাবে এটি সমাধান করে:** প্রতিটি structure-এর একটি নির্দিষ্ট, একপাক্ষিক error রয়েছে। Bloom filter কখনো উপস্থিত কোনো কিছু সম্পর্কে "উপস্থিত নেই" বলে না — তাই এগুলো একটি *negative* filter হিসেবে নিরাপদ এবং একটি *positive* filter হিসেবে অনিরাপদ। Count-Min কখনো কম অনুমান করে না। HLL symmetric কিন্তু সীমাবদ্ধ। error-এর দিক জানা আপনাকে ঠিক বলে দেয় কোন সিদ্ধান্তগুলো আপনি নিরাপদে এর ওপর অর্পণ করতে পারেন, এবং standard নিরাপদ pattern হলো: কাজ এড়িয়ে যেতে অনুমান ব্যবহার করুন, এবং যখন এটি "হয়তো" বলে তখন নির্ভুল source দিয়ে নিশ্চিত করুন।

## যে মূল্য আপনাকে দিতে হয়

- **আপনি নির্ভুল উত্তর ফিরে পেতে পারবেন না।** এগুলো একমুখী compression। মূল আইটেমগুলো পুনরুদ্ধার করার কোনো উপায় নেই, এবং কোনো নির্দিষ্ট ভুল উত্তর সংশোধন করারও উপায় নেই।
- **প্যারামিটারগুলো আগে থেকে নির্দিষ্ট এবং পরিবর্তন করা কঠিন।** 1 মিলিয়ন আইটেমের জন্য আকার দেওয়া একটি Bloom filter 10 মিলিয়নে খারাপভাবে degrade করে — false positive rate ততক্ষণ বাড়তে থাকে যতক্ষণ না এটি সবকিছুর জন্য "হয়তো" বলে এবং কোনো মূল্য প্রদান করে না। আপনাকে আগে থেকে cardinality অনুমান করতে হবে, অথবা একটি scalable variant ব্যবহার করতে হবে।
- **স্ট্যান্ডার্ড Bloom filter মুছে ফেলতে পারে না।** একটি bit সাফ করলে অন্য একটি আইটেমের membership সরে যেতে পারে। Counting Bloom filter কয়েকগুণ বেশি মেমরি খরচে deletion সাপোর্ট করে।
- **সংখ্যাগুলো ব্যাখ্যা করা একটি product সমস্যা।** "ইউনিক ভিজিটর: প্রায় 4.82M" stakeholder-দের কাছ থেকে প্রশ্ন আমন্ত্রণ জানায় যারা নির্ভুলতা আশা করে, এবং একটি dashboard যা একটি অনুমানকে অনুমান হিসেবে লেবেল দেয় না তা শেষ পর্যন্ত কোন সংখ্যাটি সঠিক তা নিয়ে একটি তর্কের কারণ হবে।
- **একটি নির্দিষ্ট স্কেলের নিচে এগুলো অপ্রয়োজনীয়।** 100,000 আইটেমের একটি `HashSet` কয়েক মেগাবাইট এবং একদম নির্ভুল। সেই আকারে একটি sketch-এর নাগাল নেওয়া বিনা কারণে error এবং জটিলতা যোগ করে। এগুলো মিলিয়ন-থেকে-বিলিয়ন পরিসরে তাদের স্থান অর্জন করে, তার আগে নয়।

## কখন এটি প্রয়োজন — এবং কখন নয়

| ব্যবহার | যার জন্য | যার জন্য নয় |
|---|---|---|
| **Bloom filter** | অনুপস্থিত key-এর জন্য ব্যয়বহুল লুকআপ এড়িয়ে যাওয়া; cache penetration ডিফেন্স; LSM read path; "আমরা কি এই URL crawl করেছি?" | এমন যেকোনো সিদ্ধান্ত যেখানে একটি false positive ক্ষতি করে |
| **HyperLogLog** | স্কেলে ইউনিক গণনা (ভিজিটর, ডিভাইস, টার্ম), dimension জুড়ে mergeable | নির্ভুল গণনা; সদস্যদের নিজেদের পুনরুদ্ধার করা |
| **Count-Min Sketch** | Heavy hitter, trending detection, একটি stream-এ আনুমানিক per-key frequency | বিরল আইটেমের নির্ভুল গণনা |

## কেন এটি interview-এ আসে

এগুলো শক্তিশালী differentiator কারণ এগুলো দেখায় আপনি শুধু সঠিকতা নয়, resource খরচ সম্পর্কেও চিন্তা করেন। এগুলো বেশ কয়েকটি standard prompt-এ স্বাভাবিকভাবে আসে: একটি URL shortener ("এই short code কি ব্যবহার করা হয়েছে?" — Bloom filter), একটি news feed ("এই ইউজার কি এই পোস্টটি দেখেছে?" — Bloom filter), analytics ("দৈনিক ইউনিক ইউজার" — HyperLogLog), এবং trending topics ("top K hashtag" — Count-Min Sketch)। একজন candidate যিনি একটি প্রস্তাব করেন *এবং* এর error বৈশিষ্ট্য বলেন এবং কেন এখানে সেই error গ্রহণযোগ্য তা বলেন, তিনি ঠিক সেই trade-off চিন্তাভাবনা প্রদর্শন করছেন যা system design interview মূল্যায়ন করার জন্য তৈরি।

## এটি কীভাবে সংযুক্ত

Bloom filter হলো **LSM-tree** storage engine-এর (বিষয় 38) একটি ভার-বহনকারী উপাদান এবং **caching**-এ (বিষয় 17) cache penetration-এর একটি standard প্রতিকার। তিনটিই **Redis**-এ (বিষয় 19) built-in, যা এগুলোকে theoretical-এর পরিবর্তে ব্যবহারিক করে তোলে। এগুলো **stream processing**-এ (বিষয় 23) ব্যাপকভাবে ব্যবহৃত হয়, যেখানে সীমাবদ্ধ মেমরি একটি কঠোর constraint, এবং এগুলো খুব উচ্চ key cardinality-তে **rate limiting**-কে (বিষয় 25) সমর্থন করে। এগুলো **URL shortener**-এ (বিষয় 48) এবং **news feed** (বিষয় 51) কেস স্টাডিতে দেখা যায়।
