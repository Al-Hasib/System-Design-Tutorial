# এই টপিক কেন গুরুত্বপূর্ণ: Observability — Logging, Metrics & Distributed Tracing

> **এক বাক্যে:** একটি monolith-এ আপনি একটি debugger সংযুক্ত করেন; একটি distributed সিস্টেমে আপনার কাছে যা আছে তা হলো সিস্টেমটি চলার সময় নিজের সম্পর্কে যা বলেছিল শুধু তাই, তাই এটি যা রেকর্ড করেনি তা চিরস্থায়ীভাবে অজানা।

## এই ধারণার আগের জগৎ

রাত ৩টা। একজন গ্রাহক জানান যে checkout মাঝেমধ্যে ব্যর্থ হচ্ছে — হয়তো বিশটির মধ্যে একটি request। আপনার সিস্টেমে বারোটি service আছে।

আপনি একটি box-এ SSH করেন এবং একটি log tail করেন। এটি সেকেন্ডে হাজার হাজার লাইনে স্ক্রল হয়ে যায়, বহু সমান্তরাল request থেকে একে অপরের সাথে মিশ্রিত, একজন ব্যবহারকারীর যাত্রা আলাদা করার কোনো উপায় ছাড়াই। আপনি জানেন না বারোটির মধ্যে কোন service দোষী, তাই আপনি এটা আরও এগারোবার পুনরাবৃত্তি করেন। Dashboard গড় latency দেখায় 120 ms — স্বাস্থ্যকর — কারণ 8 সেকেন্ড নেওয়া 5% request একটি গড়ে অদৃশ্য থাকে। কিছুই আপনাকে বলে না এটা এক ঘণ্টা আগে শুরু হয়েছে নাকি গত মঙ্গলবার।

শেষ পর্যন্ত আপনি অনুমান করেন, একটি service পুনরায় চালু করেন, এবং দেখেন symptom বন্ধ হয় কিনা। কখনো কখনো হয়, যা আপনাকে কিছুই শেখায় না এবং কারণটা যেখানে ছিল সেখানেই রেখে দেয়।

## এটি যেসব সমস্যা সমাধান করে

### ১. একাধিক service জুড়ে একটি request অনুসরণ করার কোনো উপায় নেই
**আপনি যা দেখেন:** একটি ধীর বা ব্যর্থ request, এবং বারোটি আলাদা log stream যাদের মধ্যে কোনো সংযোগ নেই।

**কেন এটা ঘটে:** প্রতিটি service স্বাধীনভাবে log করে। Service A-এর log line-কে Service G-এর log line-এর সাথে যুক্ত করার মতো কিছু নেই, যদিও দুটোই একই user action থেকে এসেছে।

**Distributed tracing কীভাবে এটা সমাধান করে:** একটি trace ID প্রান্তে (edge) তৈরি হয় এবং প্রতিটি downstream call-এর মধ্য দিয়ে প্রচারিত হয়, প্রতিটি service তার নিচে span রেকর্ড করে। আপনি সম্পূর্ণ পথ দেখানো একটি একক view পান, প্রতিটি hop-এ ব্যয় করা সময়সহ। "request-টি 8 সেকেন্ড নিয়েছে এবং তার 7.6 সেকেন্ড inventory service-এ database query-র জন্য অপেক্ষায় ছিল" — এমন একটি উত্তর আপনি অন্য কোনোভাবে পেতে পারেন না। একটি microservices architecture-এ, tracing কোনো "থাকলে ভালো" জিনিস নয় — এটা সেই stack trace-এর প্রতিস্থাপন যা আপনি monolith ভাঙার সময় হারিয়েছিলেন।

### ২. গড় যা সমস্যা লুকিয়ে রাখে
**আপনি যা দেখেন:** Dashboard গুলো ভালো দেখাচ্ছে যখন ব্যবহারকারীরা অভিযোগ করছে।

**কেন এটা ঘটে:** একটি গড় সাধারণ ক্ষেত্র দ্বারা প্রভাবিত হয়। যদি 95% request 50 ms নেয় এবং 5% request 10 সেকেন্ড নেয়, তাহলে গড় হয় 545 ms — এমন একটি সংখ্যা যা কোনো প্রকৃত request-কে বর্ণনা করে না এবং এই বাস্তবতা লুকিয়ে রাখে যে বিশজনের মধ্যে একজন ব্যবহারকারীর অভিজ্ঞতা ব্যবহারের অযোগ্য।

**Percentile metrics কীভাবে এটা সমাধান করে:** p50, p95, p99, এবং p99.9 distribution-এর আকৃতি দেখায়। p99 হলো যেখানে আপনার সবচেয়ে খারাপভাবে সেবা পাওয়া ব্যবহারকারীরা থাকে, এবং বড় স্কেলে সেগুলো অনেক মানুষ — একশ request-এর মধ্যে একটি, এবং একশ *session*-এর মধ্যে একটির চেয়ে অনেক বেশি, যেহেতু একটি session অনেক request করে। গড়ের বদলে tail latency ট্র্যাক করা একটি দলের করতে পারা সবচেয়ে উচ্চ-মূল্যের পরিবর্তনগুলোর একটি।

### ৩. স্বাভাবিক থেকে অস্বাভাবিক আলাদা করার কোনো উপায় নেই
**আপনি যা দেখেন:** একটি error rate 0.3%। এটা কি ঠিক আছে? কেউ জানে না, কারণ কেউ জানে না গত সপ্তাহে এটা কত ছিল।

**কেন এটা ঘটে:** সংরক্ষিত time-series data ছাড়া কোনো baseline নেই, তাই প্রতিটি সংখ্যা ব্যাখ্যার অযোগ্য এবং প্রতিটি incident তদন্ত শূন্য থেকে শুরু হয়।

**Metrics কীভাবে এটা সমাধান করে:** সস্তা, ক্রমাগত সংগৃহীত সাংখ্যিক series ইতিহাসসহ আপনাকে গতকাল, গত সপ্তাহ, এবং শেষ deploy-এর সাথে তুলনা করতে দেয়। এটাই alerting-কেও সম্ভব করে তোলে — alert একটি পরিচিত baseline থেকে বিচ্যুতিতে trigger হয়, এবং ব্যবহারকারীরা আসলে অনুভব করে এমন symptom-এ, প্রতিটি ক্ষণস্থায়ী ওঠানামায় নয়।

### ৪. Logs যা খোঁজা বা correlate করা যায় না
**আপনি যা দেখেন:** `Error processing order`-এর মতো ফ্রি-টেক্সট log line, কোনো order ID, কোনো user ID, কোনো trace ID এবং কোনো সামঞ্জস্যপূর্ণ format ছাড়াই।

**কেন এটা ঘটে:** Logging একটি terminal পড়া মানুষের জন্য লেখা হয়েছিল, বিলিয়ন লাইন query করা একটি machine-এর জন্য নয়।

**Structured logging কীভাবে এটা সমাধান করে:** সামঞ্জস্যপূর্ণ field name সহ key-value record (JSON) নির্গত করুন, সবসময় trace ID অন্তর্ভুক্ত করে, এবং সেগুলোকে একটি কেন্দ্রীয় store-এ পাঠান। এখন আপনি query করতে পারেন — "গত এক ঘণ্টায় সব service জুড়ে user 4821-এর সব error" — বারোটি machine grep করার বদলে। Trace ID হলো সেই join key যা logs, metrics, এবং traces-কে তিনটি আলাদা সিস্টেমের বদলে একটি সিস্টেম বানায়।

## যে মূল্য আপনাকে দিতে হয়

- **এটা সত্যিকার অর্থেই ব্যয়বহুল।** Observability data প্রায়ই এটি যে infrastructure পর্যবেক্ষণ করে তার চেয়ে বেশি খরচ করে। Log ingestion এবং retention-এর জন্য vendor বিল একটি সাধারণ বাজেট বিস্ময়, এবং প্রতিকারগুলো — trace sampling, কঠোর retention tier, metrics-এ cardinality limit — প্রতিটিই পরে প্রশ্নের উত্তর দেওয়ার কিছু ক্ষমতা বিনিময় করে।
- **Instrumentation প্রকৃত ইঞ্জিনিয়ারিং কাজ।** Thread, async boundary, এবং queue hop জুড়ে context propagation খুঁতখুঁতে এবং নীরবে ভেঙে যাওয়া সহজ। Auto-instrumentation সাহায্য করে কিন্তু সবকিছু কভার করে না।
- **Performance overhead।** প্রতিটি request trace করা CPU এবং network খরচ করে, যে কারণে sampling বিদ্যমান — এবং যে কারণে আপনি সবচেয়ে বেশি তদন্ত করতে চান এমন request-টিই হতে পারে যেটা sample করা হয়নি। Tail-based sampling (ফলাফল দেখার পরে সিদ্ধান্ত নেওয়া) সাহায্য করে, উচ্চতর খরচে।
- **High-cardinality metrics বিস্ফোরিত হয়।** user ID দিয়ে লেবেল করা একটি metric প্রতি user-এ একটি series তৈরি করে এবং আপনার metrics backend-কে ফেলে দিতে পারে। Cardinality শৃঙ্খলা একটি বারবার ঘটা অপারেশনাল শিক্ষা।
- **Logs গোপন তথ্য এবং ব্যক্তিগত data ফাঁস করে।** Request body, header, এবং token একটি অনুসন্ধানযোগ্য store-এ শেষ হয় যা বিস্তৃত দর্শকদের কাছে অ্যাক্সেসযোগ্য। এটা একটা বাস্তব এবং সাধারণ compliance ব্যর্থতা।
- **Alert fatigue মূল্য ধ্বংস করে।** অনেক বেশি alert, অথবা কারণের উপর alert (symptom-এর বদলে), মানুষকে pager উপেক্ষা করতে প্রশিক্ষিত করে। একটি কোলাহলপূর্ণ alerting setup কোনো alerting-এর চেয়েও খারাপ।

## এটা কেন Interview-এ আসে

Observability হলো ডিজাইনের সেই অংশ যা সিস্টেম তৈরি করেছে এমন মানুষদের কাগজে ডিজাইন করেছে এমন মানুষদের থেকে আলাদা করে। এটা খুব কমই মূল প্রশ্ন এবং প্রায়ই শেষের প্রশ্ন: "আপনি কীভাবে জানবেন এটা ভেঙে গেছে?" বা "আপনি এখানে একটি ধীর request কীভাবে debug করবেন?" প্রার্থী যারা স্বতঃপ্রণোদিতভাবে correlation ID সহ tracing, গড়ের বদলে percentile-based SLO, এবং symptom-based alerting-এর কথা বলেন তারা প্রায় ত্রিশ সেকেন্ডে অপারেশনাল পরিপক্বতা প্রদর্শন করেন। একটি microservices ডিজাইনে, tracing-এর কথা একেবারেই না বলা একটি লক্ষণীয় ফাঁক।

## এটা কীভাবে সংযুক্ত

Observability বাধ্যতামূলক হয়ে ওঠে যেই মুহূর্তে আপনি **microservices** (topic 30) এবং **event-driven architecture** (topic 22) গ্রহণ করেন, কারণ দুটোই local stack trace ধ্বংস করে। এটাই আপনাকে **circuit breaker এবং timeout** (topic 26) প্রকৃত latency data দিয়ে টিউন করতে, **cache hit rate** (topic 17) যাচাই করতে, **replication lag** (topic 13) এবং consumer lag (topic 20) পর্যবেক্ষণ করতে, এবং **compaction**-চালিত latency spike (topic 38) সনাক্ত করতে দেয়। এটা নিরাপদ **zero-downtime deploy** (topic 45) এবং **chaos engineering** (topic 46)-এর পূর্বশর্ত — আপনি এমন একটি experiment চালাতে পারবেন না যা আপনি পরিমাপ করতে পারেন না।
