# এই বিষয়টি কেন গুরুত্বপূর্ণ: Database Replication

> **এক বাক্যে:** একটি একক database আপনার ব্যবসার প্রতিটি byte ধারণ করে এমন একটি মেশিনে যা শেষ পর্যন্ত ব্যর্থ হবেই — replication হলো কীভাবে আপনি সেটি থেকে বেঁচে যান, এবং সাথে বোনাস হিসেবে, কীভাবে read scale করেন।

## এই ধারণার আগের জগৎ

একটি database server। এতে আছে আপনার ব্যবহারকারী, আপনার অর্ডার, আপনার পুরো পণ্য। নিজেকে দুটি প্রশ্ন করুন:

1. রাত ৩টায় সেই disk নষ্ট হয়ে গেলে কী হয়? সেরা ক্ষেত্রেও, আপনি গতরাতের backup restore করেন এবং ব্যবসা কয়েক ঘণ্টা অফলাইন থাকার সময় এক দিনের ডেটা হারান।
2. read ট্রাফিক ১০ গুণ বাড়লে কী হয়? যে একটিমাত্র মেশিন প্রতিটি read সার্ভ করে সেটিই প্রতিটি write-ও সার্ভ করে। Read, write-কে অনাহারে রাখে, write, read-কে ব্লক করে, এবং উভয়ই ধীর হয়ে যায়।

শুধুমাত্র backup কোনোটিরই সমাধান নয়। একটি backup হলো একটি point-in-time কপি; সেটি restore করা ধীর এবং lossy। Replication হলো একটি *ক্রমাগত আপডেট হওয়া* কপি যা ইতিমধ্যেই চলমান।

## এটি যেসব সমস্যা সমাধান করে

### ১. একটি হার্ডওয়্যার ব্যর্থতা থেকে সম্পূর্ণ ডেটা ক্ষতি
**আপনি যা দেখবেন:** একটি disk নষ্ট হয়ে যায়। সর্বশেষ backup ১৪ ঘণ্টা পুরনো। চৌদ্দ ঘণ্টার অর্ডার হারিয়ে গেছে এবং তা পুনর্গঠন করা যাবে না।

**কেন এটি ঘটে:** সব ডেটা ঠিক একটি জায়গায় বিদ্যমান।

**Replication কীভাবে এটি সমাধান করে:** একটি replica ক্রমাগতভাবে primary-র পরিবর্তনগুলো প্রয়োগ করে, ফলে একটি দ্বিতীয় (বা তৃতীয়) শারীরিকভাবে পৃথক কপি সবসময় মাত্র কয়েক সেকেন্ড পিছিয়ে থাকে। Primary হারানো মানে সেকেন্ড হারানো, ঘণ্টা নয় — এবং replica-কে tape থেকে restore করার পরিবর্তে ট্রাফিক সার্ভ করার জন্য promote করা যায়।

### ২. Read লোড যা write path-কে পিষে ফেলে
**আপনি যা দেখবেন:** পণ্য পাতায় একটি ট্রাফিক spike checkout ধীর করে দেয়, কারণ read এবং write একই CPU, memory, এবং buffer pool-এর জন্য প্রতিযোগিতা করে।

**কেন এটি ঘটে:** একটি মাত্র node সবকিছু সার্ভ করে, এবং বেশিরভাগ workload read-প্রধান — প্রায়ই ৯০-৯৯% read।

**Replication কীভাবে এটি সমাধান করে:** read replica-দের দিকে এবং write primary-র দিকে নির্দেশ করুন। read ক্ষমতা বাড়াতে প্রায় লিনিয়ারভাবে replica যোগ করুন। একটি read-heavy সিস্টেম scale করার এটিই সবচেয়ে সাশ্রয়ী উপায় এবং sharding-এর অনেক আগেই এটি চেষ্টা করা উচিত, যা অনেক বেশি আক্রমণাত্মক।

### ৩. রক্ষণাবেক্ষণের সময় downtime
**আপনি যা দেখবেন:** প্রতিটি database upgrade, schema পরিবর্তন, বা OS patch মানেই একটি maintenance window।

**কেন এটি ঘটে:** একমাত্র node-এ কাজ করা মানে একমাত্র node-এ downtime।

**Replication কীভাবে এটি সমাধান করে:** একটি replica upgrade করুন, যাচাই করুন, তারপর সেটিতে failover করুন। রক্ষণাবেক্ষণ একটি outage-এর পরিবর্তে একটি নিয়ন্ত্রিত switch হয়ে যায়। একই প্রক্রিয়া ব্যয়বহুল analytics এবং backup একটি replica-তে চালানো সক্ষম করে যাতে সেগুলো কখনো গ্রাহককে সার্ভ করা মেশিনকে স্পর্শ না করে।

### ৪. পৃথিবীর অন্য প্রান্তের ব্যবহারকারীদের জন্য latency
**আপনি যা দেখবেন:** Singapore-এর ব্যবহারকারীরা প্রতি query-তে ২৫০ ms অপেক্ষা করেন কারণ database Virginia-তে অবস্থিত।

**কেন এটি ঘটে:** পদার্থবিজ্ঞান। একটি সাগর পার হওয়া round-trip time-এর একটি সর্বনিম্ন সীমা থাকে।

**Replication কীভাবে এটি সমাধান করে:** ভৌগোলিকভাবে বিতরণকৃত read replica স্থানীয় read স্থানীয়ভাবেই সার্ভ করে। Write এখনও primary-তে যেতে হয়, যে কারণে write-heavy বৈশ্বিক অ্যাপগুলোর শেষ পর্যন্ত multi-primary বা multi-region ডিজাইন দরকার হয়।

## যে মূল্য আপনাকে দিতে হয়

এখানেই replication সত্যিকার অর্থে আকর্ষণীয় হয়ে ওঠে, এবং যেখানে interview-তে যাচাই করা হয়:

- **Replication lag এবং stale reads।** Asynchronous replication মানে একটি replica মিলিসেকেন্ড — বা, লোডের অধীনে, বহু সেকেন্ড — পিছিয়ে থাকতে পারে। একজন ব্যবহারকারী তার প্রোফাইল আপডেট করেন, write primary-তে যায়, redirect একটি replica থেকে read করে, এবং তার পরিবর্তন যেন উধাও হয়ে গেছে বলে মনে হয়। এই "read-your-own-writes" লঙ্ঘনটিই চিরায়ত বাগ, এবং সমাধানগুলো (write-এর পর অল্প সময়ের জন্য একজন ব্যবহারকারীর read primary-তে পাঠানো, অথবা read-your-writes token ব্যবহার করা) সবই জটিলতা যোগ করে।
- **Synchronous replication latency-র মূল্য নেয়।** replica-দের acknowledge করার জন্য অপেক্ষা করে আপনি lag দূর করতে পারেন, কিন্তু এখন প্রতিটি write সবচেয়ে ধীর replica-র network round trip-এর মূল্য দেয়, এবং একটি ধীর replica পুরো সিস্টেমকে অবনতি ঘটায়। Semi-synchronous (একাধিকের মধ্যে একটির জন্য অপেক্ষা করা) হলো সাধারণ আপোষ।
- **Failover কঠিন এবং বিপজ্জনক।** একটি primary সত্যিই মারা গেছে নাকি সাময়িকভাবে অপ্রাপ্য, তা সনাক্ত করা সত্যিই কঠিন। ভুল করলে আপনি পাবেন **split-brain**: দুটি node উভয়ই write গ্রহণ করছে, একে অপরের থেকে বিচ্যুত হচ্ছে, এবং পরে মেলানোর কোনো পরিচ্ছন্ন উপায় নেই। এই কারণেই গুরুত্বপূর্ণ সেটআপগুলো একটি timeout এবং আশার বদলে consensus-ভিত্তিক leader election ব্যবহার করে।
- **Multi-primary মানে conflicts।** দুটি node-এ write গ্রহণ করার মানে দুজন ব্যবহারকারী ভিন্ন ভিন্ন জায়গায় একই সাথে একই row আপডেট করতে পারে। কাউকে না কাউকে সেটি সমাধান করতে হয় — last-write-wins (নীরবে ডেটা হারায়), application-level merge (জটিল), অথবা CRDTs (বিশেষায়িত)। Master-master যতটা মনে হয় ততটা বিনামূল্যের সুবিধা নয়।
- **খরচ।** প্রতিটি replica প্রকৃত হার্ডওয়্যারে আপনার ডেটার একটি সম্পূর্ণ কপি।

## কখন এটি দরকার — এবং কখন নয়

| Replicate করুন যখন | অপেক্ষা করুন যখন |
|---|---|
| ডেটা হারানো অগ্রহণযোগ্য (প্রায় সবসময়ই, production-এ) | এটি একটি dev/staging পরিবেশ |
| workload read-heavy এবং read-ই bottleneck | Write-ই bottleneck — আপনার দরকার sharding, replica নয় |
| একটি দীর্ঘ restore ছাড়াই আপনার failover দরকার | ডেটা অন্য একটি উৎস থেকে সম্পূর্ণভাবে পুনর্গঠনযোগ্য |
| ব্যবহারকারীরা ভৌগোলিকভাবে ছড়িয়ে আছে | সবাই একটি অঞ্চলে এবং latency ঠিক আছে |

## এটি কেন Interview-তে আসে

Replication এমন একটি জায়গা যেখানে interviewer-রা যাচাই করে আপনি *পরিণতি* বোঝেন কিনা, শুধু component নয়। যে কেউ বলতে পারে "read replica যোগ করুন।" Follow-up প্রশ্নগুলোই মানুষকে আলাদা করে: একজন ব্যবহারকারী একটি lagging replica থেকে তার নিজের write পড়লে কী হয়? আপনি কীভাবে primary ব্যর্থতা সনাক্ত করবেন? split-brain কী এবং আপনি কীভাবে এটি এড়াবেন? synchronous replication-এর খরচ কী? জিজ্ঞাসা করার আগেই read-your-own-writes সমস্যাটি স্বেচ্ছায় উত্থাপন করা একটি database আলোচনায় সিনিয়রিটির সবচেয়ে স্পষ্ট একটি সংকেত।

## এটি কীভাবে সংযুক্ত

Replication হলো ডেটা স্তরে **fault tolerance** এবং **availability**-র পেছনের বাস্তব প্রক্রিয়া। এটি বেশিরভাগ বাস্তব সিস্টেমে **eventual consistency**-র সরাসরি কারণ, যা এটিকে **CAP theorem**-এর ব্যবহারিক রূপ করে তোলে। নিরাপদ failover-এর জন্য দরকার **consensus algorithms** (Raft/Paxos)। এটি **sharding**-এর সাথে জোড়া লাগে — এবং এর থেকে ভিন্নও: replication availability এবং read scale-এর জন্য একই ডেটা কপি করে; sharding write scale-এর জন্য ভিন্ন ভিন্ন ডেটা ভাগ করে। বাস্তব সিস্টেমগুলো উভয়ই ব্যবহার করে, এবং **multi-region architecture** হলো সবচেয়ে বড় স্কেলে replication।
