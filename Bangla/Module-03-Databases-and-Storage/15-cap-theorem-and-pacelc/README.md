# CAP Theorem ও PACELC ব্যাখ্যা

**কঠিনতার মাত্রা:** Intermediate/Advanced

## শেখার লক্ষ্য (Learning Objectives)

এই ভিডিও শেষে, আপনি সক্ষম হবেন:

- Consistency, Availability, এবং Partition Tolerance-কে ঠিক যেভাবে CAP theorem শব্দগুলো ব্যবহার করে, সেভাবে সংজ্ঞায়িত করতে।
- কেন একটি বাস্তব distributed system-এ partition tolerance আসলে কোনো পছন্দের বিষয় নয়, এবং কেন CAP কার্যকরভাবে CP বনাম AP-তে গিয়ে দাঁড়ায়, তা ব্যাখ্যা করতে।
- বাস্তব database (MongoDB, HBase, ZooKeeper, Cassandra, DynamoDB)-গুলোকে CP বা AP-এর দিকে ঝুঁকে থাকা হিসেবে শ্রেণীবদ্ধ করতে, কারণসহ।
- PACELC extension এবং কেন এটি শুধু CAP-এর চেয়ে বেশি সম্পূর্ণ মডেল, তা ব্যাখ্যা করতে।
- এই trade-off গুলো একটি বাস্তব দৃশ্যকল্পে প্রয়োগ করতে, যেমন একটি shopping cart বা একটি banking ledger।

## স্ক্রিপ্ট (Script)

### Hook/ভূমিকা

ঠিক আছে। তো গত দুটি ভিডিওতে, আমরা কিছুটা ঝুঁকিপূর্ণ একটা কাজ করেছি। আমরা আমাদের ডেটা নিয়ে সেটা ছড়িয়ে দিয়েছি। Replication ভিডিওতে, আমরা একাধিক মেশিন জুড়ে এর কপি তৈরি করেছি। Sharding ভিডিওতে, আমরা এটিকে একাধিক মেশিন জুড়ে টুকরো টুকরো করে ভাগ করেছি। এই দুটি কৌশলই একটি সিস্টেমকে বেশি scalable এবং বেশি resilient করে তোলে — কিন্তু দুটোই একই লুকানো খরচ বহন করে: এখন আপনার ডেটা একাধিক জায়গায় থাকে, যা একটি network দিয়ে সংযুক্ত। আর network ব্যর্থ হয়।

সেই একটিমাত্র সত্য — যে network অনির্ভরযোগ্য — সেটাই distributed systems-এর মধ্যে সবচেয়ে ভুল বোঝা, সবচেয়ে বেশি উদ্ধৃত, এবং interview-তে সবচেয়ে প্রাসঙ্গিক একটি ধারণার দরজা: CAP theorem। এবং আমরা দেখব, CAP আসলে গল্পের *সরলীকৃত* সংস্করণ। এর চেয়ে বেশি সূক্ষ্ম, বেশি ব্যবহারিকভাবে কার্যকর একটি extension আছে যার নাম PACELC, যা বেশিরভাগ ইঞ্জিনিয়ার কখনো শেখেন না কিন্তু প্রতিটি ইঞ্জিনিয়ারের শেখা উচিত। চলুন শুরু করি।

### CAP Theorem

CAP theorem প্রস্তাব করেছিলেন Eric Brewer, প্রায় 2000 সালের দিকে, এবং পরবর্তীতে এটি আনুষ্ঠানিকভাবে প্রমাণিত হয়েছিল। এটি বলে যে যেকোনো distributed data store একসাথে এই তিনটির মধ্যে শুধু দুটি guarantee দিতে পারে:

**Consistency** — প্রতিটি read সবচেয়ে সাম্প্রতিক write পায়, অথবা একটি error পায়। "চূড়ান্তভাবে সঠিক" নয় — আপনি যে node-কেই জিজ্ঞেস করুন না কেন, প্রত্যেকে একই, up-to-date উত্তর দেয়, যেন ডেটার মাত্র একটিই কপি আছে।

**Availability** — যে কোনো request যা একটি সচল node-এ পৌঁছায়, সেটি একটি response পায়। কোনো error নয়, কোনো timeout নয় — একটি প্রকৃত response, এমনকি সিস্টেম যদি একটি degraded অবস্থায়ও থাকে।

**Partition Tolerance** — node-গুলোর মধ্যেকার network যখন message drop করে বা সম্পূর্ণরূপে বিচ্ছিন্ন হয়ে যায়, তখনও সিস্টেম কাজ চালিয়ে যায়। একটি partition-কে দুটি data center-এর মাঝে হঠাৎ তৈরি হওয়া একটি গভীর খাদ হিসেবে ভাবুন — তারা কিছু সময়ের জন্য একে অপরের সাথে একেবারেই কথা বলতে পারে না।

এখানে ক্লাসিক "দুটি বেছে নাও" প্রস্তাবনা: C+A, C+P, অথবা A+P। কিন্তু এখানে একটা জিনিস আছে যা মানুষকে বিভ্রান্ত করে, এবং এই পুরো ভিডিওর সবচেয়ে গুরুত্বপূর্ণ অন্তর্দৃষ্টি: partition tolerance আসলে ঐচ্ছিক নয়। যেকোনো distributed system-এ — অর্থাৎ একাধিক node, যারা একটি প্রকৃত network-এর মাধ্যমে কথা বলছে — সেখানে partition কোনো না কোনো সময় *ঘটবেই*। একটি ক্যাবল কেটে যায়, একটি router খারাপ আচরণ করে, একটি data center সংযোগ হারায়, একটি process এতটাই ধীর হয়ে যায় যে তাকে unreachable বলে মনে হয়। আপনি যদি আদৌ একটি distributed system তৈরি করেন, তাহলে আপনাকে সেই বাস্তবতা সহ্য করতেই হবে; শুধু খুব বেশি চাইলেই আপনি P-কে এড়িয়ে যেতে পারবেন না।

তাই আসল, ব্যবহারিক পছন্দটা হলো "তিনটির মধ্যে কোন দুটি" নয় — বরং এটি: **যখন সত্যিই একটি partition ঘটে, তখন আপনি কি Consistency ত্যাগ করবেন নাকি Availability ত্যাগ করবেন?** এই কারণেই মানুষ আসলে বলেন CAP হলো CP বনাম AP। P ছাড়া C+A শুধুমাত্র একটি একক মেশিনের কল্পনার জগতে বিদ্যমান, অথবা এমন একটি network-এ যা কখনো ব্যর্থ হয় না — আর আমরা কল্পনার উপর সিস্টেম তৈরি করি না।

### CP System গভীরভাবে

একটি CP system, যখন একটি partition আঘাত করে, consistency সংরক্ষণ করার পথ বেছে নেয় এবং availability ত্যাগ করে। নির্দিষ্টভাবে: একটি node যদি বাকি cluster-এর সাথে নিশ্চিত করতে না পারে যে তার কাছে সর্বশেষ ডেটা আছে, তাহলে এটি আপনাকে বাসি বা ভুল কিছু দেওয়ার ঝুঁকি না নিয়ে বরং জবাব দিতে অস্বীকার করবে। এটি আপনাকে মিথ্যা বলার চেয়ে বরং বলবে, "দুঃখিত, আমি এখন আপনাকে সাহায্য করতে পারছি না।"

ভালো উদাহরণ: ZooKeeper, etcd, এবং HBase হলো ক্লাসিক CP system — এগুলো প্রায়ই বিশেষভাবে ব্যবহৃত হয় *কারণ* এগুলো strongly consistent, যেমন leader election এবং configuration management-এর মতো কাজের জন্য, যেখানে দুটি node সত্য নিয়ে দ্বিমত পোষণ করলে তা বিপর্যয়কর হবে। MongoDB, তার default configuration-এ majority write concern এবং read concern নিয়ে, CP-এর দিকেও ঝুঁকে থাকে — যদি একটি primary বেশিরভাগ replica-র কাছে পৌঁছাতে না পারে, তাহলে এটি এমন write সার্ভ করা চালিয়ে যাওয়ার বদলে সরে দাঁড়ায় যা হয়তো হারিয়ে যেতে পারে।

মানসিক মডেল: একটি ব্যাংক ভল্টের কথা ভাবুন যার একটিমাত্র combination আছে, যেটি খুলতে manager এবং assistant manager দুজনেরই উপস্থিত থাকা প্রয়োজন। যদি assistant manager-এর সাথে যোগাযোগ করা না যায়, ভল্টটি তালাবদ্ধই থাকবে, এমনকি সেটা অসুবিধাজনক হলেও। সুবিধার চেয়ে সঠিকতা।

### AP System গভীরভাবে

একটি AP system একেবারে উল্টো কাজ করে: যখন একটি partition আঘাত করে, এটি request-এর জবাব দেওয়া চালিয়ে যাওয়ার পথ বেছে নেয়, এমনকি যদি এর মানে হয় যে বিভিন্ন node আপনাকে ভিন্ন, সম্ভবত বাসি, উত্তর দিতে পারে। এটি "এখানে একটা উত্তর আছে" — এমনকি সামান্য পুরনো হলেও — বলার পথ বেছে নেবে, জবাব দিতে অস্বীকার করার বদলে।

Cassandra এবং DynamoDB হলো পাঠ্যপুস্তকীয় AP উদাহরণ। দুটোই স্পষ্টভাবে "সর্বদা-চালু" availability-র জন্য ডিজাইন করা হয়েছিল — Amazon আক্ষরিক অর্থেই Dynamo (DynamoDB-এর পেছনের paper) তৈরি করেছিল কারণ একবার একটি partition-সম্পর্কিত outage-এর মানে ছিল যে গ্রাহকরা তাদের shopping cart-এ item যোগ করতে পারছিলেন না, এবং বিক্রি হারানোটা পরে মাঝেমধ্যে conflicting cart data মিলিয়ে নেওয়ার চেয়ে খারাপ ছিল। দুটি সিস্টেমই আপনাকে একটি partition-এর সময় read এবং write চালিয়ে যেতে দেয়, এবং পরে তারা vector clocks, last-write-wins, বা version reconciliation-এর মতো জিনিস ব্যবহার করে conflict সমাধান করে।

মানসিক মডেল: এমন একটি সুবিধাজনক দোকানের চেইনের কথা ভাবুন যেটি ইন্টারনেট আউটেজের সময় একটি স্থানীয় কাগজের খাতা ব্যবহার করে gift card বিক্রি চালিয়ে যায়, এবং সংযোগ ফিরে এলে headquarters-এর সাথে balance মিলিয়ে নেয়। গ্রাহকরা সেবা পান। কোথাও একটা double-spend হওয়ার কিছু ঝুঁকি আছে, কিন্তু ব্যবসাটি সিদ্ধান্ত নিয়েছে যে সেই ঝুঁকিটা মূল্যবান।

### সাধারণ ভুল ধারণা

এখানে একটা জিনিস আছে যা প্রায় সবাইকে ফাঁদে ফেলে: CAP theorem **শুধুমাত্র** একটি প্রকৃত network partition-এর সময়কার আচরণ নিয়ে। এটি বাকি সময় একটি সিস্টেম কীভাবে আচরণ করে সে সম্পর্কে কিছুই বলে না — যা, বেশিরভাগ ভালোভাবে চলা সিস্টেমের জন্য, প্রায় পুরো সময়ই। একটি সিস্টেম কোনো স্থায়ী, সর্বক্ষণিক অর্থে "একটি CP system" বা "একটি AP system" নয়; এটি *একটি partition ঘটার মুহূর্তে* কী ত্যাগ করবে সে সম্পর্কে একটি নির্দিষ্ট পছন্দ করে। স্বাভাবিক কার্যক্রমের সময়, কোনো partition না থাকলে, আপনি অবশ্যই consistency এবং availability দুটোই একসাথে পেতে পারেন। CAP শুধু আপনাকে বলে যে network ভেঙে গেলে কী ভাঙে।

সেই ফাঁক — "যখন কোনো partition নেই, তখন বাকি 99.9% সময় কী ঘটে?" — সেটাই ঠিক যা CAP theorem উত্তর দেয় না। আর সেটাই ঠিক সেই ফাঁক যা পূরণ করার জন্য PACELC ডিজাইন করা হয়েছিল।

### PACELC পরিচিতি

PACELC, Daniel Abadi-র তৈরি করা, এই ধারণাটিকে এভাবে বিস্তৃত করে:

**P**artition — যদি একটি partition থাকে, তাহলে **A**vailability এবং **C**onsistency-র মধ্যে বেছে নিন (এই অংশটা শুধু CAP)।

**E**lse — যদি কোনো partition না থাকে, অর্থাৎ সিস্টেম স্বাভাবিকভাবে চলছে, তাহলে **L**atency এবং **C**onsistency-র মধ্যে বেছে নিন।

সেই দ্বিতীয় অর্ধেকটাই হলো অনুপস্থিত অংশ। এমনকি একটি নিখুঁতভাবে সুস্থ network দিয়েও, তখনও একটি trade-off থেকে যায়: আপনি কি একটি write নিশ্চিত করার আগে সব replica-র acknowledgment-এর জন্য অপেক্ষা করবেন (উচ্চতর consistency, উচ্চতর latency), নাকি একটি node-এ পৌঁছানোর সাথে সাথেই নিশ্চিত করে দেবেন এবং বাকিদের ব্যাকগ্রাউন্ডে sync করবেন (নিম্ন latency, দুর্বলতর consistency guarantee)? এটি একটি সত্যিকারের, প্রাত্যহিক ইঞ্জিনিয়ারিং সিদ্ধান্ত, partition থেকে সম্পূর্ণ আলাদা।

এই কারণেই PACELC-কে বাস্তবে বেশি সম্পূর্ণ এবং বেশি কার্যকর বলে মনে করা হয়: এটি বিরল, নাটকীয় failure-mode trade-off (P) এবং প্রতিটি একক request-এ ঘটতে থাকা ধ্রুবক, প্রাত্যহিক trade-off (E) — উভয়টিকেই ধারণ করে।

চলুন কিছু বাস্তব সিস্টেমকে PACELC মানচিত্রে বসাই:

- **DynamoDB** হলো PA/EL — একটি partition-এর সময় এটি availability-কে অগ্রাধিকার দেয়, এবং স্বাভাবিক কার্যক্রমের সময় এটি কড়া consistency-র চেয়ে কম latency-কে অগ্রাধিকার দেয় (যদিও এটি একটি ঐচ্ছিক strongly-consistent read mode প্রদান করে, যদি আপনি latency-র খরচ দিতে ইচ্ছুক থাকেন)।
- **Cassandra** টিউনযোগ্য, কিন্তু default-এ এটিও PA/EL-এর দিকে ঝুঁকে থাকে — আপনি প্রতিটি query-তে consistency level (ONE, QUORUM, ALL) সামঞ্জস্য করতে পারেন এবং সরাসরি latency-কে consistency-র বিনিময়ে দিতে পারেন।
- **MongoDB**, majority write/read concern দিয়ে configure করা, PC/EC-এর দিকে ঝুঁকে থাকে — এটি একটি partition-এর সময় এবং স্বাভাবিক কার্যক্রমের সময়, উভয় ক্ষেত্রেই consistency-কে অগ্রাধিকার দেয়, খরচ হিসেবে অতিরিক্ত latency এবং কমে যাওয়া availability মেনে নিয়ে।

### বাস্তব-জীবনের উদাহরণ

একটি বৈশ্বিক e-commerce "add to cart" সার্ভিসের কথা কল্পনা করুন, যা বিভিন্ন অঞ্চল জুড়ে replicate করা। একটি network partition দুই মিনিটের জন্য US এবং EU data center-কে বিচ্ছিন্ন করে দেয়। যদি এই সিস্টেমটি AP হয়, প্যারিসের একজন ক্রেতা item যোগ করতে থাকতে পারেন — তার request EU replica-তে পৌঁছায়, যা কেবল স্থানীয়ভাবে জবাব দেয়। হয়তো, একটি বিরল প্রান্তিক ঘটনায়, US পাশে সবেমাত্র stock শেষ হয়ে যাওয়া একটি item তবুও cart-এ যোগ হয়ে যায়, এবং সেটা checkout-এর সময় মিলিয়ে নেওয়া হয়। বিরক্তিকর, কিন্তু টিকে থাকার মতো, আর ব্যবসাটি বিক্রি চালিয়ে যেতে পেরেছে।

এখন দুটি account-এর মধ্যে টাকা স্থানান্তরকারী একটি ব্যাংকের কথা কল্পনা করুন। যদি সেই সিস্টেমটি একটি partition-এর সময় available থেকে যায়, তাহলে আপনি একই balance দুটি বিচ্ছিন্ন replica থেকে দুইবার খরচ হয়ে যাওয়ার ঝুঁকি নিচ্ছেন — সেটা কোনো বিরক্তিকর প্রান্তিক ঘটনা নয়, সেটা একটি প্রকৃত আর্থিক এবং নিয়ন্ত্রক সমস্যা। এখানে, একটি ব্যাংক সাধারণত CP বেছে নেবে: partition-এর সময়, প্রভাবিত transaction-টি শুধু ব্যর্থ হয় বা আটকে যায়, একটি অসামঞ্জস্যপূর্ণ balance-এর ঝুঁকি নেওয়ার বদলে। একই মূল theorem, সম্পূর্ণ ভিন্ন পছন্দ, কারণ ভুল হওয়ার খরচ সম্পূর্ণভাবে ভিন্ন।

### সংক্ষিপ্ত পুনরালোচনা (Recap)

চলুন এটা একসাথে বেঁধে ফেলি। CAP theorem বলে যে একটি network partition-এর সময়, একটি distributed system-কে Consistency এবং Availability-র মধ্যে বেছে নিতে হয় — partition tolerance নিজেই ঐচ্ছিক নয়, তাই এটা আসলে একটা CP বনাম AP সিদ্ধান্ত। CP system-গুলো বাসি হওয়ার ঝুঁকি না নিয়ে জবাব দিতে অস্বীকার করে; AP system-গুলো জবাব দিতে থাকে এবং পরে মিলিয়ে নেয়। কিন্তু CAP শুধু বিরল partition দৃশ্যকল্প বর্ণনা করে। PACELC বাকিটা পূরণ করে: এমনকি partition ছাড়াও, আপনি সবসময় Latency-কে Consistency-র বিনিময়ে দিচ্ছেন। DynamoDB, Cassandra, এবং MongoDB-র মতো বাস্তব সিস্টেমগুলো PA/EL থেকে PC/EC স্পেকট্রামের ভিন্ন ভিন্ন বিন্দুতে বসে থাকে, এবং কোন বিন্দুটা "সঠিক" তা সম্পূর্ণভাবে নির্ভর করে যে ভুল হওয়ার খরচ আপনার ব্যবসার জন্য কতটা, ধীর বা unavailable হওয়ার খরচের তুলনায়।

### এরপর কী

এখন যেহেতু আমরা বুঝি *কেন* distributed system আমাদের একসাথে নিখুঁত consistency এবং নিখুঁত availability দিতে পারে না, স্বাভাবিক পরবর্তী প্রশ্নটি হলো: database transaction model গুলো আসলে কীভাবে এই trade-off গুলোকে আনুষ্ঠানিক রূপ দেয়? পরবর্তী ভিডিওতে, আমরা ACID বনাম BASE নিয়ে গভীরে যাব — এই transaction guarantee মডেলগুলো সরাসরি এই consistency-বনাম-availability উত্তেজনা থেকেই উদ্ভূত হয়েছে — সেইসাথে normalization এবং denormalization, ডেটা-মডেলিং সিদ্ধান্তগুলো যা এগুলোর সাথে হাত ধরে চলে। সেখানে দেখা হবে।

## মূল বিষয়সমূহ (Key Takeaways)

- CAP theorem: Consistency, Availability, Partition tolerance-এর মধ্যে দুটি বেছে নিন — কিন্তু যেহেতু বাস্তব distributed system-এ partition অনিবার্য, ব্যবহারিক পছন্দটি হলো CP বনাম AP।
- CP system-গুলো (ZooKeeper, etcd, HBase, majority concern সহ MongoDB) সঠিকতা নিশ্চিত করার জন্য একটি partition-এর সময় availability ত্যাগ করে।
- AP system-গুলো (Cassandra, DynamoDB) request সার্ভ করা চালিয়ে যাওয়ার জন্য একটি partition-এর সময় কড়া consistency ত্যাগ করে, পরে conflict মিলিয়ে নেয়।
- CAP শুধুমাত্র একটি সক্রিয় network partition-এর *সময়কার* আচরণ বর্ণনা করে — এটি স্বাভাবিক কার্যক্রমের অনেক বেশি সাধারণ পরিস্থিতি সম্পর্কে কিছুই বলে না।
- PACELC CAP-কে বিস্তৃত করে: একটি Partition-এর সময় Availability বা Consistency বেছে নিন, Else (স্বাভাবিক কার্যক্রম) Latency বা Consistency বেছে নিন — যা একটি সিস্টেমের design trade-off-এর আরও পূর্ণাঙ্গ চিত্র দেয়।
- "সঠিক" পছন্দটি একটি ব্যবসায়িক সিদ্ধান্ত, কোনো প্রযুক্তিগত সিদ্ধান্ত নয়: বাসি/ভুল ডেটার খরচের সাথে downtime বা ধীরগতির খরচ তুলনা করুন।
