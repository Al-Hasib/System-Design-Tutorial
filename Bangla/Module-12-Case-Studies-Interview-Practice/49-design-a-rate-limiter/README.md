- "design a rate limiter" এর জন্য একটি সম্পূর্ণ system design interview শুরু থেকে শেষ পর্যন্ত চালানো: requirements, estimation, high-level design, deep dive, trade-offs।
- Module 6 থেকে token bucket, leaky bucket, এবং sliding window algorithm গুলোকে একটি বাস্তব distributed architecture-এ প্রয়োগ করা, প্রতিটি layer-এর জন্য সঠিকটি বেছে নেওয়া।
- একটি Redis-backed distributed counter design করা যা শত শত stateless gateway instance জুড়ে সঠিক থাকে, race condition এড়াতে atomic Lua script ব্যবহার করে।
- retry করা request গুলোর জন্য idempotency নিয়ে, এবং rate limiter নিজেই unavailable হয়ে গেলে fail-open বনাম fail-closed আচরণ নিয়ে যুক্তিসঙ্গতভাবে চিন্তা করা।
- scale-এ rate limiter-এর প্রকৃত bottleneck গুলো চিহ্নিত করা — hot keys, clock skew, এবং accuracy/performance trade-off — এবং নির্দিষ্ট design সিদ্ধান্তগুলোকে সমর্থন করা।

## Script

### Hook / Intro

আপনি algorithm গুলো পড়েছেন। আপনি token bucket-কে leaky bucket থেকে আলাদা করতে জানেন, এবং হোয়াইটবোর্ডে sliding window counter আঁকতে পারেন। কিন্তু একজন interviewer শুধু algorithm দেখতে চান না — তারা দেখতে চান আপনি এমন একটি rate limiter বানাতে পারেন কিনা যা একটি বাস্তব production system-এর সংস্পর্শে টিকে থাকে: শত শত API gateway instance, কোটি কোটি ব্যবহারকারী, এবং এই বাস্তব সম্ভাবনা যে আপনার Redis cluster রাত ২টায় ভেঙে পড়তে পারে। এই ভিডিওটি ঠিক সেটাই করে। আমরা একটি সম্পূর্ণ mock interview চালাচ্ছি, শুরু থেকে শেষ পর্যন্ত, ক্লাসিক প্রশ্নটির জন্য: "আমাদের API-এর জন্য একটি rate limiter design করুন।" আমরা requirements স্পষ্ট করব, বাস্তব সংখ্যা দিয়ে system-এর আকার নির্ধারণ করব, architecture স্কেচ করব, দুই বা তিনটি component গভীরভাবে বিশ্লেষণ করব যা আসলে একটি senior উত্তরকে junior উত্তর থেকে আলাদা করে, এবং তারপর সততার সাথে আলোচনা করব যে কোথায় এই design ভেঙে পড়ে। এটি একটি capstone ভিডিও — এটি ধরে নেয় যে আপনি ইতিমধ্যে Module 6 থেকে algorithm গুলো জানেন, তাই আমরা token bucket শুরু থেকে আবার derive করব না; আমরা এটিকে একটি building block হিসেবে ব্যবহার করছি।

### Step 1: Clarify Requirements

প্রতিটি ভালো interview উত্তর এখান থেকে শুরু হয়, কোনো diagram দিয়ে নয়। Functionally, আমাদের একসাথে বেশ কয়েক ধরনের limit সমর্থন করতে হবে: authenticated traffic-এর জন্য per-user limit, anonymous বা unauthenticated caller-দের throttle করার জন্য per-IP limit, এবং তৃতীয় পক্ষের integration-এর জন্য per-API-key limit যাদের ভিন্ন ভিন্ন contract tier থাকতে পারে — একটি free tier যা প্রতি মিনিটে ১০০ request-এ সীমাবদ্ধ, একটি paid tier প্রতি মিনিটে ১০,০০০-এ। আমরা per-endpoint granularity-ও চাই, কারণ `/login` এবং `/password-reset`-এর জন্য `/search`-এর চেয়ে অনেক কঠোর limit দরকার, ঠিক এই কারণে যে এগুলো credential-stuffing attack-এর জন্য আকর্ষণীয় লক্ষ্যবস্তু। যখন একজন client limit-এর বেশি যায়, তখন contract হলো একটি standard HTTP `429 Too Many Requests` response যার সাথে একটি `Retry-After` header থাকে যা client-কে বলে কখন আবার আসতে হবে। নিয়মগুলো redeploy ছাড়াই configurable হতে হবে — product এবং security team প্রায়ই limit পরিবর্তন করে।

Non-functionally, তিনটি constraint design-কে প্রাধান্য দেয়। প্রথমত, scale: এটিকে পুরো API gateway fleet জুড়ে সঠিকভাবে কাজ করতে হবে, একটিমাত্র box-এ নয়। দ্বিতীয়ত, latency overhead: rate-limiter check literally system-এর প্রতিটি request-এর hot path-এ বসে থাকে, তাই এটির microsecond যোগ করা উচিত, millisecond নয়। তৃতীয়ত, এবং এটিই সেই বিষয় যা candidate-রা প্রায়শই বাদ দিয়ে যায় — availability। rate limiter হলো shared infrastructure-এর একটি অংশ যা ১০০% traffic স্পর্শ করে; যদি এটি একটি single point of failure হয়ে যায়, তাহলে একটি rate limiter outage একটি সম্পূর্ণ API outage-এ পরিণত হয়, যা এটি যে abuse প্রতিরোধ করার জন্য তৈরি হয়েছিল তার চেয়েও খারাপ ফলাফল। আমরা পরে স্পষ্টভাবে এই failure mode-এর জন্য design করব।

### Step 2: Capacity Estimation

আসুন সংখ্যা বসাই। ধরুন API fleet peak সময়ে বিশ্বব্যাপী প্রতি সেকেন্ডে ১ কোটি (10 million) request handle করে, প্রায় ৫০০টি API gateway instance জুড়ে ছড়িয়ে থাকে — প্রতি instance-এ প্রায় ২০,০০০ requests per second। প্রতিটি request-এর জন্য একটি rate-limit check দরকার। আমরা যদি naively প্রতিটি request-কে একটি কেন্দ্রীভূত Redis cluster-এর বিরুদ্ধে check করতাম, তাহলে সেটা হতো প্রতি সেকেন্ডে ১ কোটি Redis operation — এবং একটি ভালোভাবে tune করা single Redis node সর্বোচ্চ প্রায় ১,০০,০০০-২,০০,০০০ ops/sec-এ পৌঁছায়, তাই একটি exact, synchronous check-every-request design-এর জন্য শুধু তাল মিলিয়ে চলতে প্রায় ৫০-১০০টি shard লাগবে, durability-র জন্য replication নিয়ে কথা বলার আগেই। এই সংখ্যাটাই আমাদের গুরুত্বপূর্ণ কিছু বলে দেয়: প্রতিটি request-এ পুরো precision, একটি logical store-এর বিরুদ্ধে, scale করে না — আমাদের পরে এটা শিথিল করতে হবে।

এখন memory। ধরুন আমরা ৫ কোটি (50 million) ইউনিক rate-limit key ট্র্যাক করছি — active user, API key, এবং IP bucket মিলিয়ে। একটি sliding-window-counter scheme ব্যবহার করে, প্রতিটি key-এর প্রয়োজন মোটামুটি দুটি integer (current window count, previous window count) এবং একটি timestamp, হয়তো ২৪ বাইট প্রকৃত data, কিন্তু একটি hash বা string entry-র জন্য Redis-এর per-key overhead আরও ৬০-৯০ বাইট লাগায়। মোটামুটি ১২০ বাইট প্রতি key ধরুন। পাঁচ কোটি key গুণ ১২০ বাইট প্রায় ৬ GB working set, যা কয়েকটি Redis node জুড়ে সহজে shard করা যায়, এবং এতটাই ছোট যে প্রায় সম্পূর্ণটাই memory-তে replica-র জন্য জায়গাসহ রাখা যায়। তাই memory এখানে কঠিন constraint নয়; shared store-এ sustained write throughput-ই আসল সমস্যা।

### Step 3: High-Level Design

Client request গুলো একটি load balancer-এ আঘাত করে, তারপর একটি API gateway instance-এ পৌঁছায় — এই কোর্সের আগের load-balancing এবং API-gateway ভিডিওগুলোতে যে layer কভার করা হয়েছিল সেটাই। gateway একটি rate-limiter component হোস্ট করে, হয় embedded middleware হিসেবে অথবা একটি দ্রুত sidecar call হিসেবে, যা request-এর identity (user ID, IP, বা API key) সেই identity এবং endpoint-এর জন্য configured limit-এর বিরুদ্ধে check করে। সেই check একটি কেন্দ্রীভূত, sharded Redis cluster দ্বারা সমর্থিত হয় যা প্রকৃত counter গুলো ধরে রাখে, যাতে ৫০০টি gateway instance-এর মধ্যে যেটাতেই একজন client-এর request পৌঁছাক না কেন, তারা সবাই একই shared state read এবং write করে। যদি request limit-এর নিচে থাকে, এটি উপযুক্ত downstream microservice-এ forward করা হয়; যদি এটি limit-এর বেশি হয়, gateway short-circuit করে এবং তাৎক্ষণিকভাবে `429` return করে, downstream service-কে কখনো বিরক্ত না করেই। সেই একটি বিস্তারিত বিষয় — edge-এ reject করা, call graph-এর গভীরে নয় — এটাই মূল কারণ কেন rate limiting প্রথম স্থানেই gateway-তে থাকে।

### Step 4: Deep Dive

**প্রতিটি layer-এর জন্য algorithm choice, Module 6 থেকে।** আমরা সর্বত্র একটি algorithm ব্যবহার করি না। gateway-তে, token bucket ডিফল্ট: এটি এমন client-এর bursty-কিন্তু-বৈধ traffic pattern সহ্য করে যে কিছুক্ষণ idle থাকার পর হঠাৎ একগুচ্ছ call ছোঁড়ে, একই সাথে একটি steady long-run rate কার্যকর রাখে — এটাই সেই আচরণ যা আমরা Stripe এবং AWS API Gateway-র public rate-limit design-এ দেখেছি। যেসব endpoint-এর জন্য একটি fragile downstream system-এ কঠোরভাবে smoothed outflow দরকার, সেখানে আমরা পরিবর্তে leaky bucket ব্যবহার করি, যা একটি constant rate-এ queue করে এবং drain করে। এবং যেখানে perfect precision-এর চেয়ে memory cost বেশি গুরুত্বপূর্ণ, sliding window counter একটি সত্যিকারের sliding log-কে সস্তায় approximate করে — ঠিক সেই trade-off যা আমরা rate-limiting-algorithms ভিডিওতে দেখিয়েছিলাম।

**Redis-এ atomically, distributed counter।** এই অংশটিই আসলে senior উত্তরকে junior উত্তর থেকে আলাদা করে। একটি naive "counter পড়ো, check করো, বাড়াও" হলো তিনটি আলাদা operation, এবং concurrency-র অধীনে এটি একটি race condition — দুটি request উভয়েই ১০০-এর limit-এর বিপরীতে ৯৯-এর একটি count পড়তে পারে এবং উভয়ই admit হতে পারে, নীরবে client-কে নির্ধারিত rate-এর দ্বিগুণে যেতে দেয়। সমাধান হলো পুরো check-and-increment-কে একটি একক atomic Lua script-এ push করা যা Redis-এর `EVAL`-এর মাধ্যমে execute হয়, যাতে read, token-refill math, এবং decrement একটি অবিভাজ্য operation হিসেবে Redis-এর single-threaded execution engine-এ ঘটে। এখানেই Module 3-এর CAP/PACELC trade-off বাস্তবে দেখা যায়: একটি rate limiter-এর প্রতিটি replica জুড়ে strict linearizable consistency দরকার হয় না — এটির perfect global precision-এর চেয়ে low latency এবং availability অনেক বেশি দরকার, ঠিক এই কারণেই team-গুলো প্রতিটি request-এ একটি consensus round trip-এর মূল্য দেওয়ার পরিবর্তে Redis-এর default availability-favoring, eventually-consistent replication-এর দিকে ঝোঁকে।

**Idempotency এবং retries, Module 6 থেকে।** Client-রা retry করে। যদি একটি request client-side-এ timeout হয় কিন্তু আসলে server-এ সফল হয়ে থাকে, এবং client এটি retry করে, তাহলে সেই retry কি একটি দ্বিতীয় token খরচ করা উচিত? যদি retry করা operation নিজেই idempotent হয় (একটি idempotency key দ্বারা identified), rate limiter-এর উচিত duplicate টি চিনতে পারা এবং যেটি logically একটি request, তার জন্য client-এর quota দ্বিগুণ charge করা এড়ানো — নাহলে আপনার retry-safety story এবং আপনার rate-limiting story সক্রিয়ভাবে একে অপরের বিরুদ্ধে লড়াই করে, এবং flaky network শেষ পর্যন্ত ভালো-আচরণকারী client-দের শাস্তি দেয়।

**একাধিক layer-এ limit প্রয়োগ করা।** একটি production system শুধুমাত্র একটি জায়গায় rate-limit করে না। একটি client SDK একটি local, optimistic token bucket বহন করতে পারে যাতে সুস্পষ্টভাবে-ব্যর্থ request গুলো কখনো client থেকে বের হতেই না পারে, শূন্য network cost-এ তাৎক্ষণিক feedback দিয়ে। API gateway Redis-এর বিরুদ্ধে authoritative, global limit কার্যকর করে। এবং service mesh-এর ভেতরে, sidecar গুলো service-to-service limit কার্যকর করতে পারে যাতে একটি overloaded internal caller একটি shared internal dependency-কে নামিয়ে দিতে না পারে — সেই একই edge-বনাম-internal বিভাজন যা আপনি external traffic রক্ষা করা API gateway-তে দেখেছেন।

### Step 5: Bottlenecks & Trade-offs

কেন্দ্রীভূত Redis store একই সাথে সমাধান এবং নতুন bottleneck উভয়ই। একজন single viral user বা একটি single misbehaving API key একটি hash slot-এ বিশাল load কেন্দ্রীভূত করে — classic hot-key সমস্যা — এবং সামগ্রিক keyspace-এর যতই horizontal sharding করা হোক না কেন, তা একটি hot key ঠিক করতে পারে না যা সবই একটি shard-এ পড়ে। প্রতিকারের মধ্যে রয়েছে প্রতিটি gateway instance-এ local pre-aggregation (প্রতিটি request-এর পরিবর্তে প্রতি ৫০-১০০ms-এ local-এ count করে Redis-এ sync করা) এবং প্রতিটি single call-এ Redis-কে hot path থেকে সরিয়ে নেওয়ার বিনিময়ে সামান্য, bounded পরিমাণ over-admission মেনে নেওয়া — sliding window log-এর exactness-কে একটি approximate counter-এর throughput-এর জন্য বিনিময় করা, যা ঠিক Module 6-এর accuracy-বনাম-performance অক্ষ। ৫০০টি gateway instance জুড়ে distributed clock skew যেকোনো timestamp-based window calculation-এর জন্য একটি সম্পর্কিত বিপদ; token bucket implementation যেগুলো Redis Lua script-এর ভেতরে elapsed time গণনা করে, Redis-এর নিজস্ব server clock-কে একমাত্র source of truth হিসেবে ব্যবহার করে, client machine-গুলোর মধ্যে skew সম্পূর্ণভাবে এড়িয়ে যায়। এবং প্রতিটি interviewer শেষ পর্যন্ত যে প্রশ্ন করে: rate limiter নিজেই — Redis, বা এর সামনের service — যদি বন্ধ হয়ে যায় তখন কী হয়? এটি circuit breaker pattern-এর একটি সরাসরি callback: rate-limiting store-এর call গুলোকে একটি circuit breaker-এ wrap করুন, এবং যখন এটি trip করে, আপনাকে স্পষ্টভাবে বেছে নিতে হবে fail-open (request গুলোকে যেতে দেওয়া, যে overload প্রতিরোধ করার জন্য এটি তৈরি হয়েছিল সেই ঝুঁকি নিয়ে) অথবা fail-closed (সবকিছু reject করা, একটি outage নিশ্চিত করে)। বেশিরভাগ public read traffic-এর জন্য সঠিক default হলো একটি conservative local fallback limit সহ fail-open; login-এর মতো security-sensitive endpoint-এর জন্য, fail-closed সাধারণত নিরাপদ default, কারণ একজন attacker সক্রিয়ভাবে চায় limiter বন্ধ থাকুক।

### Recap

আমরা configurable tier সহ per-user, per-IP, এবং per-API-key limit নিয়ে requirements স্পষ্ট করেছি; system-কে 10M requests/sec এবং ৫ কোটি key জুড়ে প্রায় ৬ GB counter state-এ আকার দিয়েছি; rate limiter-কে API gateway-তে একটি sharded Redis cluster দ্বারা সমর্থিত করে স্থাপন করেছি; atomic Lua-based counter, idempotent retry handling, এবং client SDK থেকে gateway থেকে service mesh পর্যন্ত multi-layer enforcement গভীরভাবে বিশ্লেষণ করেছি; এবং সেসব trade-off দিয়ে শেষ করেছি যেগুলো আসলে একটি interview room-এ argue করা হয় — hot keys, clock skew, এবং fail-open বনাম fail-closed।

### What's Next

আমরা এই পুরো capstone module জুড়ে আগের building block গুলোকে concrete system-এ প্রয়োগ করে কাটিয়েছি। এরপর: WhatsApp-এর মতো একটি real-time chat application design করা, যেখানে কঠিন সমস্যাগুলো traffic throttling থেকে সরে গিয়ে message delivery নিশ্চিত করা, presence track করা, এবং offline হয়ে যাওয়া ও ফিরে আসা device জুড়ে state sync করার দিকে যায়। সেখানে দেখা হবে।

## Key Takeaways

- কিছু আঁকার আগে functional scope (per-user/IP/API-key, per-endpoint, configurable tiers) এবং non-functional constraint (scale, latency overhead, availability) স্পষ্ট করুন।
- বাস্তব সংখ্যায় capacity estimate-কে ভিত্তি করুন — request rate, Redis ops/sec ceiling, এবং প্রতি key memory — যাতে যুক্তিসঙ্গত করা যায় কেন naive design গুলো scale করে না।
- আপনার burst tolerance, strict smoothing, বা memory-cheap approximation দরকার কিনা তার উপর ভিত্তি করে প্রতিটি layer-এ token bucket, leaky bucket, বা sliding window ব্যবহার করুন।
- Redis-এ atomic Lua script গুলো অনেক stateless gateway instance জুড়ে check-then-increment race condition দূর করার standard উপায়।
- Idempotency key গুলো retry করা request-কে একজন client-এর quota দ্বিগুণ consume করা থেকে প্রতিরোধ করে।
- সবসময় failure mode design করুন: rate limiter store-এর call গুলো circuit-break করুন এবং প্রতিটি endpoint-এর sensitivity অনুযায়ী স্পষ্টভাবে fail-open বনাম fail-closed সিদ্ধান্ত নিন।
