# কেন এই বিষয়টি গুরুত্বপূর্ণ: Caching Strategies & Cache Invalidation

> **এক বাক্যে:** Caching হলো সবচেয়ে সস্তা order-of-magnitude পারফরম্যান্স জয়, এবং cache invalidation হলো সেই কারণ যার জন্য এটি এমন সব বাগেরও অন্যতম সাধারণ উৎস যা পুনরুৎপাদন করা প্রায় অসম্ভব।

## এই ধারণার আগের পৃথিবী

প্রতিটি request সবকিছু আবার গণনা করে। একটি product page একই product-এর জন্য একই ছয়টি query চালায়, সেকেন্ডে ৪,০০০ বার, একদম বাইট-বাই-বাইট অভিন্ন ফলাফল ফেরত দেয়। Database একই কাজ বারবার করে কারণ কেউ তাকে না করতে বলেনি।

সেই মুহূর্তে আপনার বিকল্পগুলো হলো একটি বড় database কেনা, shard করা, অথবা জিজ্ঞেস করা বন্ধ করা। Caching হলো "জিজ্ঞেস করা বন্ধ করা" — এবং এটা অন্য দুটোর চেয়ে অনেক বেশি সস্তা। একটি memory read microsecond-এ পরিমাপ করা হয়; নেটওয়ার্ক hop সহ একটি disk-backed database query মিলিসেকেন্ডে পরিমাপ করা হয়। সেটা ১০০-১০০০ গুণের একটি ফারাক, একটি Redis instance-এর দামে পাওয়া যায়।

## এটি যে সমস্যাগুলো সমাধান করে

### ১. একই কাজ বারবার হওয়া
**আপনি যা দেখবেন:** Database CPU পুরোপুরি ব্যস্ত, একটি query log-এ দেখা যায় একই কয়েকটি query volume-এ প্রাধান্য বিস্তার করছে।

**কেন এটা হয়:** Read-heavy workload অত্যন্ত পুনরাবৃত্তিমূলক। জনপ্রিয় item-এর একটি ছোট সেট সাধারণত ট্রাফিকের একটি বড় অংশ দখল করে থাকে।

**Caching এটা কীভাবে সমাধান করে:** একবার গণনা করুন, বহুবার সার্ভ করুন। একটি ৯৫% hit rate মানে database লোডের মাত্র ৫% দেখে — যে database-টি shard করার প্রস্তুতি নিচ্ছিলেন সেটাকেই আরামে অলস একটি database-এ পরিণত করে।

### ২. ডেটা লেয়ার দ্বারা নির্ধারিত latency floor
**আপনি যা দেখবেন:** একটি page ২০০ ms-এর নিচে যেতে পারে না কারণ এটি বেশ কয়েকটি database call করে, প্রতিটি অনিবার্যভাবে কয়েক দশ মিলিসেকেন্ড।

**কেন এটা হয়:** Disk I/O, নেটওয়ার্ক hop, এবং query planning-এর বাস্তব খরচ আছে যা কোনো পরিমাণ indexing দিয়েও পুরোপুরি দূর করা যায় না।

**Caching এটা কীভাবে সমাধান করে:** একটি in-memory lookup সাব-মিলিসেকেন্ড। এমন ডেটার ক্ষেত্রে যা সহজে সস্তায় গণনা করা যায় না, সেখানে আক্রমণাত্মক latency লক্ষ্যে পৌঁছানোর একমাত্র উপায় প্রায়শই caching।

### ৩. ব্যবহারকারীরা যে stale data দেখতে পান
**আপনি যা দেখবেন:** একজন ব্যবহারকারী তার প্রোফাইল আপডেট করেন এবং পুরনো ভার্সনটাই দেখা যেতে থাকে। একটি price পরিবর্তন এক ঘণ্টা ধরে কার্যকর হয় না। একই জিনিসের জন্য দুজন ব্যবহারকারী ভিন্ন ভিন্ন মান দেখেন।

**কেন এটা হয়:** একটি cache হলো সত্যের একটি দ্বিতীয় copy। উৎস পরিবর্তন হওয়ার মুহূর্তেই, সেই copy ভুল হয়ে যায়, এবং কিছুই স্বয়ংক্রিয়ভাবে cache-কে সেটা জানায় না।

**Invalidation স্ট্র্যাটেজি এটা কীভাবে সমাধান করে:** এটাই এই বিষয়ের মূল কেন্দ্রবিন্দু। TTL সস্তায় কিন্তু অনির্ভুলভাবে staleness-কে সীমাবদ্ধ করে। Write-এর সময় explicit invalidation নির্ভুল কিন্তু প্রতিটি write পথকে মনে রাখতে হয় — এবং যেটা ভুলে যায় সেটাই আপনাকে কামড়ায়। Write-through cache-কে সঠিক রাখে write latency-র মূল্যে। প্রতিটি স্ট্র্যাটেজি জটিলতার বিনিময়ে freshness ট্রেড করে, এবং সচেতনভাবে বাছাই করাই আসল খেলা।

### ৪. Cache failure-এর কারণে database ভেঙে পড়া
**আপনি যা দেখবেন:** cache রিস্টার্ট হয়। প্রতিটি request একই সাথে miss করে, তাদের সবাই একসাথে database-কে আঘাত করে, এবং database — যা ট্রাফিকের মাত্র ৫%-এর জন্য sized — তাৎক্ষণিকভাবে মারা যায়।

**কেন এটা হয়:** একটি cache শুধু জিনিসগুলো দ্রুত করে না; এটা আপনার capacity plan-এর একটি load-bearing অংশ হয়ে ওঠে। এটা সরিয়ে ফেললে আপনি পুরনো পৃথিবীতে ফিরে যান না, বরং এমন একটি সিস্টেমের ওপর পুরো ট্রাফিক নেমে আসে যেটাকে সেই অনুপাতে ছোট করে scale করা হয়েছিল।

**এই বিষয়টি এটা কীভাবে সমাধান করে:** এটি failure মোডগুলো এবং তাদের প্রতিকার চিহ্নিত করে। **Thundering herd / stampede** — অনেক request একই সাথে একই key miss করা — request coalescing অথবা একটি সংক্ষিপ্ত lock দিয়ে সামলানো হয়। **Cache penetration** — অস্তিত্বহীন key-র জন্য বারবার miss হওয়া — negative result cache করে বা একটি Bloom filter দিয়ে সামলানো হয়। **Cache avalanche** — অনেক key একসাথে expire হওয়া — TTL-এ jitter যোগ করে সামলানো হয়।

## যে মূল্য আপনাকে দিতে হয়

- **সত্যের একটি দ্বিতীয় উৎস।** প্রতিটি cached মান ভুল হতে পারে। আপনি গতির বিনিময়ে একটি correctness গ্যারান্টি ট্রেড করেছেন, এবং সেই নির্দিষ্ট ডেটার জন্য সেই ট্রেড গ্রহণযোগ্য হতে হবে।
- **Invalidation সত্যিই কঠিন।** এটা একটা ক্লিশে কারণ এটা সত্যি: codebase বড় হওয়ার সাথে সাথে, একটি নির্দিষ্ট cached মান invalidate করে এমন প্রতিটি কোড পথ চিরকাল মনে রাখা একটি সত্যিকারের maintenance বোঝা।
- **ডিবাগিং অনেক বেশি কঠিন হয়ে যায়।** "আমার ক্ষেত্রে কাজ করছে"-র মানে প্রায়ই দাঁড়ায় "আমার request একটি ভিন্ন cache node হিট করেছে" অথবা "আমার key expire হয়ে গিয়েছিল"। বাগগুলো বিরতিহীন এবং পরিবেশ-নির্ভর হয়ে ওঠে।
- **নতুন failure মোড।** Stampede, avalanche, এবং penetration এমন সমস্যা যা আপনার আগে ছিল না।
- **ভুল জিনিস cache করলে সবকিছুই নষ্ট হয়।** কম reuse বা বেশি churn থাকা ডেটা দ্বিতীয়বার পড়ার আগেই evict হয়ে যায় — আপনি সব জটিলতার মূল্য দেন কিন্তু কোনো hit rate পান না।

## কখন এটা দরকার — এবং কখন দরকার নেই

| যখন cache করবেন | যখন cache করবেন না |
|---|---|
| Read লেখার চেয়ে বহুগুণ বেশি | প্রায় প্রতিটি read-এই ডেটা পরিবর্তন হয় |
| একই ডেটা বারবার অনুরোধ করা হয় | প্রতিটি request অনন্য (per-user one-off) |
| মান গণনা করা ব্যয়বহুল | source query ইতিমধ্যেই সাব-মিলিসেকেন্ড |
| সামান্য stale data গ্রহণযোগ্য | correctness একদম নির্ভুল হতে হবে (balance, checkout-এ inventory) |

## এটি ইন্টারভিউতে কেন আসে

Caching প্রায় প্রতিটি ডিজাইনেই দেখা যায় যার read ট্রাফিক আছে, তাই এর *উল্লেখ করাটা* একটি ন্যূনতম প্রত্যাশা। কৃতিত্ব আসে follow-up প্রশ্ন থেকে: কোন স্ট্র্যাটেজি (cache-aside হলো যুক্তিসঙ্গত default, এবং কেন তা জানা উচিত), TTL কত এবং কেন, write-এর সময় কীভাবে invalidate করবেন, আপনার প্রত্যাশিত hit rate কত, এবং — যে প্রশ্নটি প্রার্থীদের আলাদা করে — cache ডাউন হয়ে গেলে বা cold-start করলে কী হয়। জিজ্ঞেস না করা সত্ত্বেও stampede protection নিয়ে কথা বলা প্রকৃত operational অভিজ্ঞতার ইঙ্গিত দেয়।

## এটি কীভাবে সংযুক্ত

Caching হলো প্রথম প্রতিরক্ষা লাইন যা অনেক সিস্টেমের জন্য **replication** এবং **sharding**-কে অপ্রয়োজনীয় করে তোলে। এটা একাধিক লেয়ারে implement করা হয়: edge-এ browser এবং **CDN** (topic ১৮), মাঝখানে একটি **reverse proxy**, এবং আপনার service-গুলোর পেছনে **Redis/Memcached** (topic ১৯)। একাধিক node জুড়ে একটি cache বিতরণ করতে **consistent hashing** দরকার। এবং freshness ট্রেড-অফটি **eventual consistency**-র একটি সরাসরি প্রয়োগ — একটি cache, ফর্মালি বলতে গেলে, আপনি ইচ্ছাকৃতভাবে তৈরি করা একটি eventually consistent replica।
