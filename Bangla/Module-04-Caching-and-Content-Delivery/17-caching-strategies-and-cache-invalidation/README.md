# Caching Strategies & Cache Invalidation (Cache-Aside, Write-Through, Write-Back)

**কঠিনতা মাত্রা:** Intermediate

## শেখার লক্ষ্যসমূহ

- সিস্টেম ডিজাইনে caching কেন প্রায়শই সবচেয়ে বেশি লাভজনক optimization, তা ব্যাখ্যা করা
- cache-aside, read-through, write-through, write-behind (write-back), এবং write-around স্ট্র্যাটেজিগুলোর তুলনা করা
- সাধারণ cache invalidation কৌশলগুলো এবং কেন "cache invalidation is hard" তা বর্ণনা করা
- cache eviction পলিসি (LRU, LFU, FIFO) চিহ্নিত করা এবং কখন কোনটি ব্যবহার করতে হবে তা জানা
- সাধারণ cache failure মোডগুলো চিহ্নিত করা এবং প্রশমিত করা: stampede, thundering herd, এবং stale reads

## স্ক্রিপ্ট

### Hook / ভূমিকা

কম্পিউটার সায়েন্সে একটা পুরনো রসিকতা আছে: "কম্পিউটার সায়েন্সে মাত্র দুটো কঠিন জিনিস আছে: cache invalidation এবং জিনিসের নামকরণ করা।" আজ আমরা প্রথমটা নিয়ে কথা বলব। আপনি যদি কখনো কোনো ওয়েবপেজ রিফ্রেশ করে পুরনো ডেটা দেখে থাকেন, অথবা ভেবে থাকেন Twitter কীভাবে তার ডেটাবেস গলিয়ে না ফেলে একশো কোটি মানুষকে তাদের ফিড দেখাতে পারে, তার উত্তর প্রায় সবসময়ই caching। এই ভিডিওতে আমরা প্রধান caching স্ট্র্যাটেজিগুলো ভেঙে দেখব — cache-aside, read-through, write-through, write-behind, এবং write-around — এবং তারপর সত্যিকারের কঠিন অংশ নিয়ে কথা বলব: কীভাবে ব্যবহারকারীদের ডেটার প্রতি বিশ্বাস না ভেঙে একটি cache invalidate করা যায়।

### Caching কেন গুরুত্বপূর্ণ

চলুন "কেন" দিয়ে শুরু করি। প্রতিবার যখন আপনার অ্যাপ্লিকেশনের ডেটা দরকার হয়, তখন তার দুটো পছন্দ থাকে: একটা ধীর, ব্যয়বহুল উৎস থেকে সেটা আনা — যেমন ডিস্কে থাকা কোনো database, অথবা নেটওয়ার্কের মাধ্যমে কোনো third-party API — অথবা কোথাও থেকে দ্রুত সেটা তুলে নেওয়া, যদি সেই ডেটা আগেই গণনা করা বা fetch করা থাকে। সেই "দ্রুত কোনো জায়গা"টাই হলো cache। এটা সাধারণত RAM দিয়ে সমর্থিত, এবং RAM একটা ঘূর্ণায়মান ডিস্কের চেয়ে প্রায় ১,০০,০০০ গুণ দ্রুত অ্যাক্সেস করা যায়, এবং এমনকি একটি দ্রুতগতির SSD-র চেয়েও ৫-১০ গুণ দ্রুত। তাই আপনি যদি একটি request কে ডিস্কে হিট করা কোনো database query থেকে না দিয়ে memory থেকে সার্ভ করতে পারেন, তাহলে আপনি কয়েক দশ মিলিসেকেন্ড থেকে সাব-মিলিসেকেন্ড response time-এ চলে যেতে পারেন।

কিন্তু এটা শুধু একজন ব্যবহারকারীর জন্য গতির বিষয় নয় — এটা আপনার পুরো সিস্টেমকে রক্ষা করার বিষয়ও। কল্পনা করুন এমন একটি product page যেটি সেকেন্ডে ১০,০০০ বার হিট হয়। cache ছাড়া, সেটা সেকেন্ডে ১০,০০০টি database query, সবগুলোই একই প্রশ্ন জিজ্ঞেস করছে। cache থাকলে, হয়তো প্রতি ১,০০০টি request-এর মধ্যে মাত্র ১টি আসলে database-এ পৌঁছায়, কারণ বাকি ৯৯৯টি একটি cached copy থেকে সার্ভ করা হয়। এই অনুপাত — যত শতাংশ request cache থেকে সার্ভ হয় — তাকে বলা হয় **cache hit ratio**, এবং এটি একটি caching সিস্টেমের সবচেয়ে গুরুত্বপূর্ণ সংখ্যাগুলোর একটি। ৯৫% hit ratio শুনতে চমৎকার লাগতে পারে, কিন্তু তার মানে এখনো বিশাল পরিমাণ ট্রাফিকের ৫% আপনার origin-এ পৌঁছাচ্ছে, তাই "ভালো" cache hit ratio-কেও আপনার প্রকৃত স্কেলের সাথে মিলিয়ে মূল্যায়ন করতে হবে।

### Cache-Aside (Lazy Loading)

আপনি নিজে যেটা সবচেয়ে বেশি implement করবেন সেই সবচেয়ে সাধারণ প্যাটার্নটি হলো **cache-aside**, যাকে lazy loading-ও বলা হয়। এটা কীভাবে কাজ করে দেখুন: যখন আপনার অ্যাপ্লিকেশনের ডেটা দরকার হয়, এটি প্রথমে cache চেক করে। যদি ডেটা সেখানে থাকে — একটি "cache hit" — এটি সাথে সাথেই সেটা ফেরত দেয়। যদি সেটা সেখানে না থাকে — একটি "cache miss" — অ্যাপ্লিকেশন নিজেই database query করে, ফলাফল পায়, cache-এ একটি copy লেখে, এবং তারপর সেটা caller-কে ফেরত দেয়। cache মূল ডেটা পথের "পাশে" বসে থাকে; এটা পরিচালনা করা cache-এর কাজ নয়, অ্যাপ্লিকেশনের কাজ।

cache-aside-এর ভালো দিক হলো এর সহনশীলতা: আপনার cache যদি সম্পূর্ণরূপে ডাউন হয়ে যায়, তবুও আপনার অ্যাপ কাজ করে — এটা কেবল প্রতিটি request-এর জন্য database হিট করার দিকে ফিরে যায়, যা ধীর কিন্তু ভাঙা নয়। খারাপ দিক হলো যেকোনো নির্দিষ্ট ডেটার জন্য প্রথম request সবসময় ধীর হয়, কারণ সেটাকেই cache পূরণ করতে হয়। একে বলা হয় "cold cache" সমস্যা, এবং বড় স্কেলে, যদি একই সময়ে একই missing key-র জন্য অনেক request আসে, তাহলে আপনি পাবেন একটি **cache stampede** — শত শত thread একই মুহূর্তে cache miss করছে এবং একসাথে database-কে আঘাত করছে। এটা থেকে কীভাবে রক্ষা পাওয়া যায় তা নিয়ে আমরা একটু পরেই কথা বলব।

### Read-Through Caching

**Read-through** হলো cache-aside-এর খুব কাছের একটি ভাই, কিন্তু দায়িত্ব সরে যায়। আপনার অ্যাপ্লিকেশন কোড cache চেক করে এবং তারপর miss হলে database-এ manually query করার বদলে, cache নিজেই এমনভাবে configure করা থাকে যেন এটি জানে কীভাবে database থেকে ডেটা লোড করতে হয়। আপনার অ্যাপ্লিকেশন সবসময় শুধু cache-কে জিজ্ঞেস করে, এবং প্রয়োজন হলে cache নিজে ভেতরে ভেতরে source of truth থেকে fetch করে। এতে আপনার অ্যাপ্লিকেশন কোড পরিষ্কার থাকে, কারণ লোডিং লজিক এক জায়গায় থাকে, কিন্তু এর জন্য এমন একটি caching layer দরকার যেটি এটা সমর্থন করে — অনেক managed caching service এবং library এটা প্রদান করে।

### Write-Through Caching

এখন লেখা (writes) নিয়ে কথা বলা যাক। **Write-through** caching-এ, প্রতিবার আপনার অ্যাপ্লিকেশন যখন ডেটা লেখে, এটি একই সাথে cache এবং database-এ লেখে, একটি একক লজিক্যাল অপারেশন হিসেবে, caller-কে সফলতার বার্তা ফেরত দেওয়ার আগে। এটা নিশ্চিত করে যে cache এবং database সবসময় সিঙ্কে থাকে — একটি write সম্পন্ন হওয়ার পর আপনি cache থেকে কখনো stale data পড়বেন না। এর মূল্য হলো write latency: এখন প্রতিটি write-কে একটির বদলে দুটি সিস্টেমের জন্য অপেক্ষা করতে হয়। read consistency যখন অনেক গুরুত্বপূর্ণ এবং আপনার write volume যখন মাঝারি, তখন write-through একটি ভালো পছন্দ।

### Write-Back (Write-Behind) Caching

**Write-back**, যাকে কখনো কখনো write-behind বলা হয়, বিপরীত ট্রেড-অফ নেয়। অ্যাপ্লিকেশন শুধু cache-এ লেখে, এবং cache সাথে সাথে সফলতা নিশ্চিত করে। আলাদাভাবে, asynchronously, cache সেই writeগুলো ব্যাকগ্রাউন্ডে database-এ flush করে — হয়তো batch করে, হয়তো একটি timer অনুযায়ী। এটা writeকে অত্যন্ত দ্রুত করে তোলে, কারণ আপনি ধীরগতির database-এর জন্য মোটেও অপেক্ষা করছেন না। কিন্তু এটা ঝুঁকি নিয়ে আসে: pending writeগুলো database-এ flush করার আগে যদি cache crash করে, তাহলে সেই ডেটা হারিয়ে যায়। Write-back তখন ব্যবহার করা হয় যখন write throughput সবচেয়ে গুরুত্বপূর্ণ এবং আপনি সামান্য potential data loss সহ্য করতে পারেন, অথবা আপনি cache layer-এর ভেতরেই durability তৈরি করেছেন, যেমন একটি append-only log দিয়ে।

### Write-Around Caching

শেষ প্যাটার্ন: **write-around**। এখানে, write সরাসরি database-এ যায়, cache-কে সম্পূর্ণভাবে বাইপাস করে। cache শুধুমাত্র পরবর্তী কোনো read-এ পূরণ করা হয়, cache-aside প্যাটার্ন ব্যবহার করে। এটা এমন ডেটা দিয়ে cache পূর্ণ হওয়া এড়ায় যা হয়তো আর কখনো পড়া হবে না — চিন্তা করুন এমন একটি সিস্টেমের কথা যা কোটি কোটি write-once, read-rarely ইভেন্ট লগ করে। ট্রেড-অফ হলো write-এর ঠিক পরে করা কোনো read সবসময় একটি cache miss হবে।

### Cache Invalidation

এখন, কঠিন অংশ: cached data-কে stale হওয়া থেকে আটকানো। এর তিনটি ব্যাপক পদ্ধতি আছে। **Time-based expiration (TTL)** সবচেয়ে সহজ — আপনি প্রতিটি cache entry-কে নির্দিষ্ট কিছু সেকেন্ড পরে স্বয়ংক্রিয়ভাবে expire হওয়ার জন্য সেট করেন। এটা সহজ এবং নিজে নিজে সেরে যায় (self-healing), কিন্তু সেই TTL window-এর মধ্যে, ব্যবহারকারীরা পুরনো ডেটা দেখতে পারেন। **Explicit invalidation** আরও নির্ভুল: যখনই আন্ডারলাইং ডেটা পরিবর্তন হয়, আপনার অ্যাপ্লিকেশন সক্রিয়ভাবে সংশ্লিষ্ট cache entry-কে মুছে ফেলে বা আপডেট করে। এটা আপনাকে আরও তাজা ডেটা দেয়, কিন্তু জটিলতা যোগ করে, কারণ এখন ডেটা মিউটেট করে এমন প্রতিটি কোড পথকে মনে রাখতে হবে যে cache-কেও touch করতে হবে — একটা মিস করুন, আর আপনি এমন একটি stale-data বাগ পাবেন যা খুঁজে বের করা কষ্টকর। **Write-through invalidation**, যা আমরা ইতিমধ্যে আলোচনা করেছি, প্রতিটি write-এর অংশ হিসেবে cache আপডেট রাখার মাধ্যমে এই সমস্যাটি এড়িয়ে যায়।

বাস্তবে, বেশিরভাগ production সিস্টেম একটি মিশ্রণ ব্যবহার করে: একটি নিরাপত্তা জাল হিসেবে TTL, এবং ব্যবহারকারীর সামনে থাকা এমন যেকোনো কিছুর জন্য explicit invalidation যেখানে staleness গ্রহণযোগ্য নয়, যেমন একটি account balance।

### Eviction Policies

Cache-এর মেমরি সীমিত, তাই সেগুলো পূর্ণ হয়ে গেলে, নতুন entry-র জন্য জায়গা করতে কিছু একটা evict করতে হয়। তিনটি ক্লাসিক পলিসি হলো: **LRU (Least Recently Used)**, যেটি সবচেয়ে দীর্ঘ সময় ধরে অ্যাক্সেস না হওয়া যেকোনো কিছু evict করে — বেশিরভাগ workload-এর জন্য দুর্দান্ত কারণ সম্প্রতি অ্যাক্সেস হওয়া ডেটা শীঘ্রই আবার অ্যাক্সেস হওয়ার প্রবণতা রাখে; **LFU (Least Frequently Used)**, যেটি সবচেয়ে কম মোট বার অ্যাক্সেস হওয়া যেকোনো কিছু evict করে — এটা তখন ভালো যখন recency-র চেয়ে জনপ্রিয়তা বেশি স্থিতিশীল; এবং **FIFO (First In, First Out)**, যা কতবার ব্যবহৃত হয়েছে তা বিবেচনা না করেই সবচেয়ে পুরনো entry-টি evict করে — সহজ কিন্তু প্রায়শই কম কার্যকর। উদাহরণস্বরূপ, Redis আপনাকে LRU এবং LFU ভ্যারিয়েন্ট সহ বেশ কয়েকটি eviction পলিসির মধ্যে কোনটি ব্যবহার করবেন তা configure করতে দেয়।

### বাস্তব-জগতের উদাহরণ

একটি news website-এর হোমপেজের কথা চিন্তা করুন। এটা প্রতি মিনিটে লক্ষ লক্ষ বার পড়া হয় কিন্তু editor-রা ঘণ্টায় মাত্র কয়েকবারই এটা আপডেট করেন। এটা একটি নিখুঁত cache-aside প্লাস TTL প্রার্থী: রেন্ডার করা হোমপেজটিকে, ধরুন, ৩০ সেকেন্ডের জন্য cache করুন। প্রায় প্রতিটি visitor cache থেকে তাৎক্ষণিক response পান, এবং সবচেয়ে খারাপ ক্ষেত্রে, একটি আপডেট সব জায়গায় দেখাতে ৩০ সেকেন্ড সময় নেয় — একটি সম্পূর্ণ গ্রহণযোগ্য ট্রেড-অফ। এখন এটাকে একটি shopping cart-এর সাথে তুলনা করুন: যদি কোনো ব্যবহারকারী একটি item যোগ করে, তারা আশা করে সেটা তাৎক্ষণিকভাবে, প্রতিবার, সব জায়গায় দেখতে পাবে। এর জন্য দরকার write-through বা explicit invalidation, কোনো lazy TTL নয়, কারণ সেখানে staleness সরাসরি user experience নষ্ট করে।

আরেকটি failure mode জানা দরকার: আগে যে **thundering herd** বা cache stampede সমস্যার কথা বলেছিলাম। কল্পনা করুন একটি hot cache key — বলা যাক, একজন সেলিব্রিটির প্রোফাইল — একই মুহূর্তে expire হয় যখন দশ হাজার request একসাথে আসে। সবগুলো দশ হাজার request cache miss করে এবং একই সাথে database-কে আঘাত করে। একটি সাধারণ সমাধান হলো "cache locking" বা "request coalescing": miss করা প্রথম request একটি lock গ্রহণ করে, ডেটা fetch করে, এবং cache পূরণ করে, যখন বাকি ৯,৯৯৯টি request হয় সংক্ষিপ্ত সময় অপেক্ষা করে অথবা database হিট করার বদলে সামান্য stale ডেটা পায়।

### পুনরালোচনা

চলুন সংক্ষেপে দেখি। Cache-aside হলো default, অ্যাপ্লিকেশন-পরিচালিত প্যাটার্ন যেখানে আপনি প্রথমে cache চেক করেন এবং miss হলে সেটা পূরণ করেন। Read-through সেই লজিককে cache-এর ভেতরেই স্থানান্তরিত করে। Write-through প্রতিটি write-এ cache এবং database-কে সিঙ্কে রাখে, write latency-র মূল্যে। Write-back দ্রুত কিন্তু data loss-এর ঝুঁকি নেয়। Write-around কদাচিৎ পড়া হওয়া writeগুলো দিয়ে cache দূষিত হওয়া এড়ায়। এবং আপনি যে প্যাটার্নই ব্যবহার করুন না কেন, আপনার invalidation-এর জন্য একটি পরিকল্পনা দরকার — TTL, explicit invalidation, অথবা দুটোই — এবং সেই সাথে cache পূর্ণ হয়ে গেলে LRU-র মতো একটি eviction পলিসি।

### এরপর কী

এতক্ষণ caching ছিল আপনার অ্যাপ্লিকেশন সার্ভারের কাছাকাছি ডেটা cache করা নিয়ে। কিন্তু কনটেন্ট আপনার *ব্যবহারকারীদের* কাছাকাছি cache করা নিয়ে কী, তারা বিশ্বের যেখানেই থাকুক না কেন? পরবর্তী ভিডিওতে, আমরা Content Delivery Network — CDN — এবং Cloudflare আর CloudFront-এর মতো সার্ভিসগুলো কীভাবে আপনার কনটেন্টকে বিশ্বজুড়ে edge সার্ভারগুলোতে push করে, যাতে টোকিওর একজন ব্যবহারকারীকে ভার্জিনিয়ার একটি সার্ভারের জন্য অপেক্ষা করতে না হয়, তা দেখব।

## মূল শিক্ষণীয় বিষয়

- Caching latency এবং origin load-এ একটি বিশাল হ্রাসের বিনিময়ে সামান্য staleness ঝুঁকি নেয়; RAM অ্যাক্সেস ডিস্কের চেয়ে বহুগুণ দ্রুত।
- Cache-aside (lazy loading) অ্যাপ্লিকেশন-পরিচালিত: cache চেক করুন, miss হলে database query করুন এবং cache পূরণ করুন।
- Write-through প্রতিটি write-এ cache এবং DB-কে consistent রাখে কিন্তু write latency যোগ করে; write-back দ্রুত কিন্তু flush না-হওয়া write হারানোর ঝুঁকি রাখে; write-around কদাচিৎ পড়া হওয়া writeগুলো cache করা এড়ায়।
- Invalidation স্ট্র্যাটেজি: TTL-ভিত্তিক expiration (সহজ, self-healing, কিন্তু window-এর মধ্যে stale থাকে) এবং explicit invalidation (তাজা, কিন্তু যেখানেই ডেটা পরিবর্তন হয় সেখানেই সামঞ্জস্যপূর্ণভাবে প্রয়োগ করতে হবে)।
- Eviction পলিসি (LRU, LFU, FIFO) নির্ধারণ করে যে cache পূর্ণ হয়ে গেলে কী সরানো হবে; LRU সবচেয়ে সাধারণ default।
- Cache stampede/thundering herd তখন ঘটে যখন একটি hot key expire হয় এবং অনেক request একসাথে database-কে আঘাত করে; locking, request coalescing, অথবা staggered TTL দিয়ে এটা প্রশমিত করুন।
