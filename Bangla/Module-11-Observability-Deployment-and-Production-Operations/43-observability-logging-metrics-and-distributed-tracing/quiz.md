# অনুশীলন ও Interview প্রশ্ন (Practice & Interview Questions)

**১. Monitoring এবং observability-এর মধ্যে পার্থক্য কী?**
Monitoring হলো পরিচিত failure mode/metric-এর একটি পূর্বনির্ধারিত সেট পর্যবেক্ষণ করা এবং সেগুলো একটি threshold অতিক্রম করলে alert করা — এটা সেসব প্রশ্নের উত্তর দেয় যা আপনি আগে থেকেই জিজ্ঞাসা করার কথা ভেবেছিলেন। Observability হলো বৃহত্তর ক্ষমতা — অপ্রত্যাশিত কিছু ঘটার পরে একটি সিস্টেমের অভ্যন্তরীণ অবস্থা তদন্ত এবং বোঝা, যার মধ্যে এমন failure mode-ও রয়েছে যা কেউ সুনির্দিষ্টভাবে অনুমান করেনি, প্রথমে নতুন কোড শিপ করার প্রয়োজন ছাড়াই।

**২. কেন প্রোডাকশন সিস্টেমগুলো ফ্রি-টেক্সট log line-এর বদলে structured logging-এর (যেমন JSON) দিকে এগিয়ে যায়?**
বড় স্কেলে, logs অনেক service instance জুড়ে ছড়িয়ে থাকে এবং সংখ্যায় লক্ষ লক্ষ হয়। সামঞ্জস্যপূর্ণ field (timestamp, service, request ID, severity) সহ structured logs একটি কেন্দ্রীয় aggregation সিস্টেমে পদ্ধতিগতভাবে indexed, খোঁজা এবং ফিল্টার করা যায় — ফ্রি-টেক্সট logs সেই পরিমাণে service জুড়ে খোঁজা এবং correlate করা অনেক বেশি কঠিন।

**৩. একটি metric কোন প্রশ্নের উত্তর দেয় যা একটি log দিতে পারে না, এবং উল্টোটা?**
একটি metric উত্তর দেয় "সিস্টেম সামষ্টিকভাবে, সময়ের সাথে কেমন আচরণ করছে?" (যেমন, p99 latency, error rate) সস্তায়, কারণ এটি প্রতিটি individual ঘটনা সংরক্ষণ করার বদলে আগে থেকে সমষ্টিকৃত। একটি log উত্তর দেয় "এই একটি নির্দিষ্ট ঘটনায় ঠিক কী ঘটেছে?" সম্পূর্ণ বিস্তারিতসহ, কিন্তু একটি metric যেভাবে পারে সেভাবে সামষ্টিকভাবে স্ক্যান করা ব্যবহারিক নয়।

**৪. একটি trace ID কীভাবে microservices জুড়ে distributed tracing সম্ভব করে তোলে তা ব্যাখ্যা করুন।**
একটি request প্রথম সিস্টেমে প্রবেশ করলে একটি unique trace ID তৈরি হয় এবং (সাধারণত একটি header-এর মাধ্যমে) সেই request যে প্রতিটি downstream service call trigger করে তাতে প্রচারিত হয়। প্রতিটি service একই trace ID দিয়ে ট্যাগ করা তার নিজস্ব span রেকর্ড করে তার নিজের কাজের অংশের জন্য, এবং একটি tracing টুল একটি trace ID-র সব span-কে একটি একক timeline-এ যুক্ত করে যা request-টি স্পর্শ করা প্রতিটি service জুড়ে এর সম্পূর্ণ পথ দেখায়।

**৫. Distributed tracing-এ "span" কী?**
একটি span হলো একটি trace-এর মধ্যে কাজের একটি একক — সাধারণত একটি service-এর একটি request-এর নিজের অংশ পরিচালনা — একটি start time, duration, এবং metadata সহ রেকর্ড করা, এবং সম্পূর্ণ call graph পুনর্গঠন করতে এর parent/child span-এর সাথে যুক্ত।

**৬. কেন user-facing symptom-এর উপর alerting (যেমন elevated error rate বা breached latency SLO) সাধারণত প্রতিটি সম্ভাব্য অভ্যন্তরীণ কারণে alerting করার চেয়ে ভালো?**
প্রতিটি সম্ভাব্য অভ্যন্তরীণ কারণে alerting করা (যেমন, তাত্ত্বিকভাবে একটি সমস্যা নির্দেশ করতে পারে এমন প্রতিটি metric) অনেক low-signal alert তৈরি করে, যা alert fatigue-এর দিকে নিয়ে যায় — ইঞ্জিনিয়াররা alert উপেক্ষা করা শুরু করে, এমনকি যেগুলো গুরুত্বপূর্ণ সেগুলোকেও। ব্যবহারকারীদের আসলে প্রভাবিত করে এমন symptom-এর উপর alerting করা signal-to-noise অনুপাত উচ্চ রাখে; নির্দিষ্ট অভ্যন্তরীণ root cause তখন logs, metrics, এবং traces ব্যবহার করে তদন্তের সময় খুঁজে পাওয়া যায়।

**৭. দৃশ্যকল্প: একটি microservices architecture-এ একটি একক user-facing request 8টি অভ্যন্তরীণ service-এ ছড়িয়ে যায়, এবং এটি মাঝেমধ্যে ধীর হয়। কেন স্বাধীনভাবে সংগৃহীত per-service logs এবং metrics এটি নির্ণয় করার জন্য অপর্যাপ্ত?**
Per-service logs এবং metrics প্রতিটি service-এর নিজস্ব আচরণ বিচ্ছিন্নভাবে দেখায়, কিন্তু আপনাকে বলে না এই 8টি call একটি নির্দিষ্ট ধীর request-এর সাথে কীভাবে সম্পর্কিত, বা ওই 8টির মধ্যে কোনটা ওই নির্দিষ্ট ঘটনার জন্য আসলে bottleneck ছিল। Distributed tracing প্রয়োজন সেই 8টি service-এর ওই একটি request পরিচালনাকে একটি shared trace ID দিয়ে একসাথে বাঁধতে এবং দেখতে যে ঠিক কোন span latency-র জন্য দায়ী ছিল।

**৮. একটি সিস্টেম কি ভারীভাবে monitored হতে পারে (অনেক dashboard এবং alert) এবং তবুও observable না হতে পারে? ব্যাখ্যা করুন।**
হ্যাঁ — একটি সিস্টেমের দলের অনুমান করা প্রতিটি পরিচিত failure mode কভার করা কয়েক ডজন dashboard এবং alert থাকতে পারে, তবুও observability-র অভাব থাকতে পারে যদি ওই dashboard গুলোর কোনোটাই ঘটনাক্রমে একটি novel, অপ্রত্যাশিত failure mode ক্যাপচার না করে। Observability-র জন্য যথেষ্ট সমৃদ্ধ structured logs, high-cardinality metrics, এবং tracing দরকার যাতে ঘটনার পরে নতুন কিছু তদন্ত করা যায়, শুধু একটি নির্দিষ্ট, পূর্বনির্ধারিত indicator সেট পর্যবেক্ষণ করা নয়।

**৯. কেন p99 latency প্রায়ই গড় latency-র চেয়ে alert করার জন্য বেশি উপযোগী একটি metric?**
গড় latency স্বাস্থ্যকর দেখাতে পারে যখন একটি অর্থপূর্ণ অংশের ব্যবহারকারীরা অনেক খারাপ performance অনুভব করে, কারণ কয়েকটি খুব দ্রুত request একটি গড়ে অনেক ধীর request-কে ভারসাম্য করতে পারে। p99 latency সুনির্দিষ্টভাবে সবচেয়ে খারাপ 1% request-এর অভিজ্ঞতা ক্যাপচার করে, যা একটি গড় যা লুকিয়ে রাখবে তার চেয়ে প্রকৃত user-facing কষ্টকে ভালোভাবে প্রতিফলিত করে।

**১০. সত্য নাকি মিথ্যা: একটি সিস্টেমে distributed tracing যোগ করা logs এবং metrics-এর প্রয়োজনীয়তা দূর করে দেয়।**
মিথ্যা। Logs, metrics, এবং traces প্রত্যেকে একটি ভিন্ন প্রশ্নের উত্তর দেয় এবং একে অপরের পরিপূরক, প্রতিস্থাপক নয়। Tracing আপনাকে বলে একটি request-এর পথ এবং কোথায় সময় ব্যয় হয়েছিল; আপনি তখনও ধীর span-এর ভেতরে নির্দিষ্ট error/বিস্তারিত দেখতে logs ব্যবহার করবেন, এবং সেই সামষ্টিক symptom (যেমন একটি latency spike) সনাক্ত করতে metrics ব্যবহার করবেন যা প্রথমে একটি trace তদন্ত করতে প্ররোচিত করেছিল।
