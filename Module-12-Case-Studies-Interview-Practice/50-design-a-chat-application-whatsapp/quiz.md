# Follow-Up Interview Questions — Design a Chat Application (like WhatsApp)

Use these to pressure-test your understanding after watching the video. Try answering before reading the model answer.

**1. How do you guarantee message ordering within a group chat when multiple senders are messaging concurrently?**
Assign a per-conversation monotonically increasing sequence number at write time (e.g., generated by whichever shard/partition owns that conversation ID), rather than relying on wall-clock timestamps across different servers. All messages for a conversation route through the same shard, so the sequence number can be assigned atomically there. Clients render messages sorted by sequence number, not arrival time. Perfect global ordering across all conversations is not required or attempted — only per-conversation ordering matters to users.

**2. How would you handle a user who is a member of 500 different groups?**
The main risk is presence/routing overhead and fan-out cost when many groups are active simultaneously. Store group membership in a separate, cacheable membership service (keyed by group ID) rather than duplicating member lists into every message. For fan-out, use fan-out-on-write for the user's actively-open groups and consider fan-out-on-read (compute the feed of unread messages on demand) for large or rarely-opened groups, to avoid writing 500 copies of every message the user isn't actively viewing.

**3. How do you scale to millions of concurrent WebSocket connections?**
Horizontally scale stateful Connection Gateway servers (event-loop based, e.g. Netty/Node/Go), each holding a bounded number of connections (~50,000 in our estimate), fronted by a load balancer that distributes new connections across the fleet. Maintain a Presence Service mapping user ID to the specific gateway server holding their connection, so other servers know where to route messages. Use connection draining on deploys/restarts so clients reconnect gracefully rather than dropping messages.

**4. What are the implications of end-to-end encryption (like the Signal Protocol) on server design?**
The server can no longer read message content, so it cannot do content-based features (search, spam filtering, content moderation) server-side — those either move to the client or are dropped. The server's job becomes purely routing and storing opaque encrypted blobs plus metadata (sender, recipient, timestamp) needed for delivery. Key exchange and per-device key management (see multi-device sync below) become a first-class server responsibility even though message content stays opaque.

**5. How do you handle multi-device sync (a user logged into phone, web, and desktop simultaneously)?**
Treat each device as its own "connection" registered under the same user ID in the Presence Service, so a user can have multiple active gateway connections at once. On send, fan out to all of the recipient's active devices, and also echo the message back to the sender's other devices so their history stays in sync. For end-to-end encrypted messages, this means encrypting the message separately per recipient device's public key (as Signal Protocol does), which increases fan-out cost per message.

**6. What's the difference between at-least-once and exactly-once delivery here, and which does this design use?**
At-least-once means a message might be delivered/processed more than once (e.g., due to a client retry after a timed-out ACK); exactly-once means it's processed precisely once, which is very hard to guarantee end-to-end across an unreliable network without heavy coordination. This design uses at-least-once delivery at the transport level, combined with a client-generated idempotency key (message ID) that the Chat Service deduplicates on — giving users an effectively-exactly-once experience (no duplicate bubbles) without the cost of distributed transactions.

**7. How does the system know a message was "read," and how expensive is that at scale?**
The recipient's client sends a read-receipt event (message ID + read timestamp) back through its gateway when the message is displayed. This is its own lightweight, high-frequency write path — at 20B messages/day, read receipts roughly double the metadata write volume, so they're typically batched/debounced client-side (e.g., one receipt per conversation-open rather than per message) rather than sent individually for every message.

**8. Why choose a NoSQL/wide-column store over a relational database for message history?**
The workload is append-only writes and range reads keyed by conversation ID — no need for joins or multi-row ACID transactions across conversations. Wide-column stores (Cassandra, DynamoDB-style) scale writes horizontally by partition key far more easily than a relational database, which would need heavy manual sharding to reach ~2 PB/year of metadata. The trade-off is weaker cross-row consistency guarantees, which is acceptable given the AP (availability-favoring) stance from Step 4 of the design.

**9. What happens if the Message Queue or a Connection Gateway crashes mid-delivery?**
Because the message is persisted to the Message Store before (or atomically with) being published to the queue, a crash doesn't lose it — durability comes from storage, not from the queue being reliable in the moment. If a gateway crashes, its connections drop, the Presence Service entries for that gateway become stale and are cleaned up (e.g., via heartbeat timeout), and affected clients reconnect to a healthy gateway; any messages queued for the crashed gateway are redelivered once the recipient's new gateway registers in Presence.

**10. How would you support message search without breaking the encryption/scale model?**
Server-side full-text search over encrypted content isn't possible without breaking end-to-end encryption, so search is typically done client-side over the locally-decrypted message cache (which is also why chat apps keep a local on-device database). If server-assisted search is required (e.g., for unencrypted enterprise chat variants), a separate search index (Elasticsearch-style) is built off decrypted content on the server, understanding this weakens the E2E guarantee.

**11. How do you avoid overloading the Presence Service, given it's queried on nearly every message send?**
Cache presence data aggressively (e.g., in Redis, per the caching module) with short TTLs, since "is this user online and on which gateway" changes relatively infrequently compared to message volume. Update presence on connect/disconnect events rather than polling, and treat a cache miss as "assume offline, use push" rather than blocking the send path on a slow lookup — favoring availability and low latency over perfect presence accuracy.

**12. How would you estimate and control the growth of storage over time, and what's your archival strategy?**
Track growth against the ~2 PB/year metadata estimate (plus separately-tracked media storage) and set a tiering policy: recent messages (e.g., last 30–90 days) stay in the hot, sharded, low-latency store; older messages move to cheaper cold/archival object storage indexed by conversation ID and date range, fetched on-demand when a user scrolls back far enough. This keeps the hot store's working set — and therefore its cost and latency — bounded even as total historical volume keeps growing.
